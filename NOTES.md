## 2026-07-12 (#380 — POST /todos dropped `clarified`; synced Inbox captures vanished)
- Root cause was **schema drop on upload**: `TodoCreate`/`TodoUpdate` lacked `clarified` (plus `last_clarified_at`, `next_action_text`, `last_next_action_completion_at`, `updated_at`, `created_at`); Pydantic's default `extra='ignore'` made the drop silent — a 422 would at least have surfaced via the #305 fatal-drop path — so the model default `clarified=True` won and the next checkpoint replicated the flip back over the local row. Fixing only the create path would have shipped the inverse bug (clarify PATCH dropped → task bounces back into the Inbox), so both schemas changed together.
- Two more latent drops found by the audit: the ORM model lagged migration 0024 (`next_action_text` / `last_next_action_completion_at` existed only in Postgres), and `create_todo` never passed `intent` through, so POST always stored `intent='next'` regardless of the payload.
- Column-ownership table now lives in docs/SYNC.md § The `todos` upload contract; the standing tripwire is `test_connector_shaped_payload_roundtrips_client_state` (a POST whose payload is shaped like a connector PUT: SQLite integer booleans, Drift space-before-offset timestamps). SQLite test-harness quirk: its DATETIME storage strips tz offsets on re-read, so the test's `_assert_instant` helper compares naive values by wall-clock and aware values by instant.

## 2026-07-12 (issue #382 — Alembic schema/version drift crash-loop)
- Drift healing is split two ways: migration 0024 got existence guards (re-run no-ops, so `alembic upgrade` heals the stamp itself), everything else goes through the new `app/migrate.py` startup runner, which pre-flights the stamp and classifies duplicate-object failures into an actionable diagnostic — deliberately **no** auto-`alembic stamp` (ADR-0012): a duplicate-column error proves one object exists, not that all pending migrations ran. Guards are safe to add retroactively because Alembic never checksums migration files; they stop at 0024 because non-additive migrations (data moves like 0003, drops like 0020) can't be made safely idempotent.
- (CodeRabbit follow-up) The 0024 guard validates a pre-existing column's type category + nullability before accepting it as applied — but deliberately not `DateTime.timezone`: SQLite reflection (the test harness) can't represent the flag, and a column this migration itself created carries it correctly on Postgres. `app/migrate.py`'s pre-flight reuses `app.database.engine` rather than building its own, so its connection behaviour (incl. the project-wide `connect_args={"ssl": None}`) can never drift from the app's.

## 2026-07-01 (issue #306 — user_preferences conflict resolution)
- PowerSync's write-checkpoint holds pending/uploaded CRUD mutations over the synced view (windows 1–2 in docs/SYNC.md), so plain LWW `user_preferences` keys don't need a bespoke download-arbitration pass; the residual wipe risk is window 3 (a fatal `4xx` drops the entry, then the pull deletes the local row). Production prevention of window 3 depends on backend idempotency/permissiveness so a legitimate write never `4xx`s; the loud-in-debug assert in `backend_connector.dart` only *detects* such a drop during development, it does not prevent the wipe in release.
- Snooze `*_snoozed_until` keys use `maxTimestampValue` (between two live values the later *value* wins; a clear-tombstone vs a live value is plain LWW on `updated_at` so a later re-snooze survives a stale clear), deliberately departing from blanket LWW so a stale write can't regress an active snooze floor — ADR-0011.
- The engine delete-on-server-absent behaviour is not unit-coverable: the whole Dart harness is `NativeDatabase.memory()` with no PowerSync engine. Registry logic is pure-function tested; the engine path is manual/emulator-only (docs/TESTING.md).

## 2026-07-01 (#342 — stale Inbox/Next Actions watchers after clarify-routing)
- **Root cause (confirmed by source reading).** In production `todos`/`tags`/`todo_tags` are PowerSync views with INSTEAD OF triggers, so a Drift `UpdateStatement.write` / `DeleteStatement.go` against them reports `changes() == 0` (the trigger body mutates rows, not the view). Drift gates its own `notifyUpdates` on `rows > 0` (`drift/…/statements/update.dart:39`, `delete.dart:56`), so it **never fires** for these writes. That leaves the `SqliteAsyncDriftConnection` bridge (`PowerSyncDatabase.updates` → `handleTableUpdates`) as the **sole** live-invalidation path for view-backed watchers. When that async bridge is momentarily silent on the first cold start of a new planning day (initial-sync window), all three surfaces — Inbox list, Inbox badge, Next Actions list — freeze at once until restart, exactly as reported. `customUpdate`/`customInsert` are unaffected (they notify unconditionally), which is why `markDone`/`setIntent` never showed the bug.
- **Fix.** Added `GtdDatabase.notifyTodosViewWrite({bool includeTodoTags})` (a documented wrapper over `notifyUpdates` emitting kind-less `TableUpdate`s so one call serves updates *and* deletes) and call it right after **every** direct `todos`-view `update`/`delete` in `TodoDao` / `InboxDao`: `applyRouting` (todos, plus todo_tags when person tags change), `setNextActionText`, `rescheduleTask`, `stampLastClarifiedAt`, `clearDoneAt`, `updateFields`, `InboxDao.processInboxItem`, and the `delete`-based `InboxDao.deleteTodo`. This gives Drift a second, in-process invalidation path so the live lists no longer depend solely on the bridge. Harmless idempotent re-run under `NativeDatabase` tests (where the write already reported `rows > 0`). Only `update`/`delete` are gated (`update.dart:39`, `delete.dart:55`); `into(todos).insert()` notifies unconditionally (`insert.dart:74`), as do `customUpdate`/`customInsert` methods (`markDone`, `setIntent`, `restore`) — so captures and those need no extra call.
- **Regression test** `app/test/database/clarify_routing_view_notify_test.dart` reproduces the production topology on a real on-disk sqlite_async DB: it lets Drift build the schema, then rewrites `todos` into a view over `todos_data` with INSTEAD OF triggers, and wires it through the real `SqliteAsyncDriftConnection`. Because the bridge names only the backing table (`todos_data`), never the `todos` view, the watchers can refresh after `applyRouting` **only** via Drift's own notify. Verified red-on-`main` (both `_waitUntil`s time out at 8s) and green with the fix. Faithful, deterministic, no mocks — and runnable under plain `flutter test` (the powersync core native lib isn't loadable off-device, so a full `PowerSyncDatabase` VM test isn't possible; the view+trigger model captures the exact `changes()==0` mechanism instead).
- **Generalised (CodeRabbit follow-up).** The same `rows>0` gate defeats *every* `.write()`/`.go()` on a view, so the fix now covers all direct `todos`-view writes in `TodoDao`/`InboxDao`, not just the clarify-routing trio — see ADR-0010 for the self-notify invariant. Still out of scope: writes to `tags` via `setPersonTagsForTodo` go through `todo_tags` (covered by `applyRouting`'s `includeTodoTags`) but a standalone person-tag edit path, if one is added later, must call `notifyTodosViewWrite(includeTodoTags: true)` itself.

## 2026-04-21

- `flutter_local_notifications` v21 switched `show()` and `cancel()` from positional to named parameters. The existing `cancelReminder(id: id)` call was already correct (coincidentally); new notification methods must use `show(id:, title:, body:, notificationDetails:)` and `cancel(id:)`.
- `FocusModeNotifier.startFocus` reads `databaseProvider` and `currentUserIdProvider` eagerly before the `await` to avoid the autoDispose-ref-after-await bug (same pattern established in `TaskDetailNotifier`).
- `inProgress → deferred` (Abandon) clears `selectedForToday` to false via `_buildTransitionCompanion`, so the task is immediately removed from today's focus list and returned to Next Actions.
- Universal search (issue #118) uses a Drift LEFT OUTER JOIN across todos/todo_tags/tags rather than FTS5. FTS5 content-table triggers require `AFTER INSERT ON todos` — impossible in production where `todos` is a PowerSync view (SQLite only supports `INSTEAD OF` triggers on views). LIKE + Dart-side filtering on 10k rows is fast enough (< 10ms). SearchDao is a plain class, not `@DriftAccessor`, so no `build_runner` step needed.
- In Riverpod 3.x, `StateProvider` is classified as legacy and moved to `legacy.dart` for backward compatibility. Prefer `NotifierProvider` with a one-method `Notifier` for new code — the notifier exposes an `update(T)` method that sets state, replacing the `.notifier.state = ` pattern.
- Clarify-Inbox destination buttons (Next Action / Waiting For / Someday / Done) silently did nothing in prod; only Skip worked. Root cause #1: `InboxDao.processInboxItem` asserted `updated == 1` after the UPDATE, but in prod `todos` is a PowerSync view with an INSTEAD OF UPDATE trigger. SQLite's `sqlite3_changes()` excludes writes done inside trigger bodies, so `updated` is always 0 for view UPDATEs — the assertion threw `StateError`, which `_process` in `inbox_clarification_step.dart` caught and only `debugPrint`-ed. Tests passed because `inbox_dao_test.dart` uses `NativeDatabase.memory()` (raw table, no trigger). Rule: never assert on affected-row counts for UPDATE/DELETE against PowerSync view tables (`todos`, `tags`, `todo_tags`); rely on the WHERE-clause optimistic lock instead.
- Root cause #2 for the same screen: the "Scheduled" button tried `inbox → scheduled` in one hop, but the state machine intentionally forbids it (see `gtd_state_machine_test.dart`'s `inbox → scheduled is rejected`). Scheduling means "a clarified next-action with a date", so it's conceptually two steps. Fix: `DailyPlanningNotifier.processInboxItem` does `inbox → nextAction` then `nextAction → scheduled` when the destination is `scheduled`. Kept the state machine as-is.

## 2026-04-20

- Login/register screens relied on GoRouter's `/login`→`/inbox` redirect for post-auth navigation, but when the screen is pushed on top of another route (e.g. Settings → Sign in to sync) the redirect doesn't pop the pushed entry and `_isLoading` never resets — spinner gets stuck. Fix: explicitly `context.pop()` when `canPop`, fall back to `setState(_isLoading = false)` otherwise and let the redirect take over.
- Sign-out reset `currentUserIdProvider` to `'local'` without reassigning the user's rows, so queries (all filtered by `user_id`) returned nothing and the UI promise "Your local data will remain on this device" was a lie. Fix: mirror the login-time migration — before resetting, move todos/tags/todo_tags from the real user id back to `'local'`. Round-trips cleanly through a logout/login cycle via the existing `_handleMigration`.
- First login fix wasn't enough when a conflict-resolution dialog fires: GoRouter's `/login`→`/inbox` redirect (triggered by `authStateNotifier` flipping during login) raced with the explicit `context.pop()`, and users landed back on login. Solution: drop the redirect entirely — login/register screens own their post-auth navigation (`pop` if pushed, `go('/inbox')` otherwise). Also dropped the forced `context.go('/inbox')` after logout in Settings; the `ValueListenableBuilder<authStateNotifier>` already rebuilds the sync section in place.
- Even without the redirect, `authStateNotifier` in `refreshListenable` caused the same pop-back failure: flipping it triggers a GoRouter refresh that rebuilds the route stack from the current URI, which drops imperatively-pushed entries (the `/settings` below `/login` disappears, so `canPop` flips to false mid-flow). Fix: remove `authStateNotifier` from `refreshListenable`. No redirect depends on it anymore. The bug only manifests when the conflict dialog fires (local + server data both exist), which is why a fresh install appears to work — no local data, no dialog, no race.
- Session wasn't restored across app restarts: `authTokenProvider` is an `AsyncNotifierProvider` whose `build()` reads stored tokens and flips `authStateNotifier`, but Riverpod providers are lazy. Nothing at startup watched it (router reads the raw `authStateNotifier.value`; shell/inbox only watch `currentUserIdProvider`), so the token sat in secure storage until the user opened Login/Settings. Fix: make `JeevesApp` a `ConsumerWidget` and `ref.watch(authTokenProvider)` at the root so `build()` runs at app launch. No refresh hooks needed — `currentUserIdProvider` is set inside the same `build()`, and all data providers `watch` it.
- Restoring auth at cold start left PowerSync disconnected (tasks showed but the sync icon read "local only"). `powerSyncInstanceProvider.build()` called `await applyUser(ref.read(currentUserIdProvider))` *before* setting up `ref.listen`. On cold start the read returned `'local'` (auth still in flight), and the `'local' → realUser` flip happened in the `await`'s microtask gap, before the listener was installed. Riverpod's `ref.listen` doesn't fire for existing state, so the transition was lost and PowerSync stayed disconnected. Fix: install the listener first, then do the initial apply — the existing `pending` serial chain handles any concurrent transition correctly.
- Fix #1 wasn't enough: the sync icon still showed "local only" after restart. PowerSync's `db.statusStream` emits on **changes only**, so a subscriber that attaches after the DB has already reached a stable state (as happens on cold start, when auth/PS setup finish before `syncStatusProvider`'s async\* subscribes) waits forever — `asData` stays `null` and both the navbar and Settings fall back to the "local only" cloud icon. Fix: seed the stream with `db.currentStatus` before yielding from `statusStream`.
- PowerSync exposes `todos`, `tags`, `todo_tags` as SQLite views with INSTEAD OF triggers. SQLite forbids UPSERT (`INSERT ... ON CONFLICT DO UPDATE`) on views at the parser level — even with triggers present. Use `INSERT OR REPLACE` (`InsertMode.insertOrReplace`) instead; PowerSync's triggers handle it correctly.
- The INSERT OR REPLACE fix wasn't enough for tag assignment: `TodoTags` in Drift had no `id` column, so the emitted INSERT didn't include `id`, but PowerSync's INSTEAD OF trigger writes `NEW.id` into `ps_data__todo_tags` (which has `id` as PK). Tests passed because they use `NativeDatabase` (real table, composite PK), not a PowerSync view. Fix: add `id` to `TodoTags` and derive it deterministically from `(todo_id, tag_id)` via `uuid.v5(Namespace.url, 'jeeves://todo_tag/$todoId/$tagId')` so re-assigning the same tag collapses under INSERT OR REPLACE instead of piling up junction rows.
- The accompanying `schemaVersion` bump (5→6) tripped Drift's onUpgrade at app startup: `ALTER TABLE "todo_tags" ADD COLUMN "id" TEXT NOT NULL` throws `SqliteException(1): Cannot add a column to a view` because PowerSync exposes `todo_tags` as a view. PowerSync already manages the column set via `powersyncSchema`, so the ALTER is unnecessary on prod but still required for `NativeDatabase.memory()` tests. Fix: route every `m.addColumn` through `_addColumnIfTable`, which checks `sqlite_master.type` and skips if the target is a view. Previous migrations (from<2..from<5) were switched to the helper too; they only didn't explode earlier because they never ran on an already-installed prod DB.
- After fixing the schema-and-migration side, tag assignment still did nothing silently. Real cause: `TaskDetailNotifier` held a `Ref` and did `_ref.read(databaseProvider)` in every method. `taskDetailNotifierProvider` is `Provider.autoDispose.family`; no widget watches it, so Riverpod disposes the ref between the `ref.read()` that creates the notifier and the second `_db` access after an `await`. The callback's error was hidden by `.ignore()` in the UI. Fix: capture `db` and `userId` eagerly at construction and drop `Ref` entirely — safe because `GtdDatabase` is a process-wide singleton and the task-detail screen pops on logout.
