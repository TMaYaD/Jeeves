# Product Requirements Document (PRD): GTD Execution Hybrid App

<!-- This document describes the current state of the system. Rewrite sections when they become inaccurate. Do not append change logs. -->

## 1. Product Vision
To build a hybrid productivity application that merges the rigid organizational trust of a Getting Things Done (GTD) inventory (e.g., Nirvana) with the focused, day-to-day execution layer of a daily planner and timeboxer (e.g., Sunsama). The system prioritizes immediate execution through Pomodoro constraints and maintains data integrity through forced behavioral guardrails.

## 2. Core Principles
* **Action over Organization:** The interface must drive the user toward execution, hiding the complexity of the larger GTD inventory during focus phases.
* **System Integrity is Paramount:** A productivity system fails when the data rots. The app will enforce necessary friction (guardrails) to ensure the user reviews and updates their inventory.
* **Local-First Performance:** Task capture and execution (timers/state changes) must work flawlessly offline to prevent user frustration.
* **Consistent Outcome representations:** Surfaces compose shared metadata, row, review-card and detail contracts; deliberate variations are recorded in [DESIGN.md](DESIGN.md#outcome-representations). Due dates use the local calendar day and `MMM d, y`.

## 3. Epics & Functional Requirements

### Epic 1: The GTD Inventory Engine
**Goal:** Establish a rock-solid backend for strict GTD methodology.
* **Universal Inbox:** A holding zone for all unprocessed captures.
* **Clarify Mode:** A synced, per-user preference (Settings → Clarify) selecting how the clarify act maps Captures onto Outcomes. **1-1 mode** (the default) clarifies each Capture to at most one Outcome: routing to an Intent creates exactly one Outcome and automatically marks the Capture clarified (it leaves the Inbox) at that first Outcome link, while a discard is a valid zero-Outcome clarification that marks the Capture clarified without creating anything. **n-m mode** is split/merge: the user explicitly completes each Capture and only that completion marks it clarified, so a Capture stays in the Inbox while Outcomes are carved out of it. The mode changes behaviour, never stored data — toggling mid-stream leaves every existing Capture and its links to Outcomes valid. The preference and its Settings toggle ship ahead of the n-m clarify surfaces, so selecting n-m persists and replicates but does not yet change clarify behaviour.
* **Data Schema:** Tasks must support the following metadata:
    * Project
    * Area of Responsibility (AoR)
    * Contexts (Tags)
    * Time Estimate
    * Energy Level
* **Outcome Plan (Task Detail):** The task-detail screen and the Daily Planning Outcome peek surface an Outcome's **Plan** — its ordered queue of planned Actions — above the notes area. The section anchors on the current Action (with a demote affordance to move it back into the plan) and lists the planned Actions, which can be added, reordered, edited, promoted, or removed. A planned Action carries its own **energy level** and **time estimate**, set alongside its phrase in the add/edit sheet and shown on the row as chips; they travel with the Action through promotion, so estimating a step the user has not started yet is the point rather than a side effect. Planned Actions are never engageable (they do not appear on Next / Waiting For / Focus / Today's Plan), but are offered for **promotion** wherever the app asks what's next — the Outcome's detail view, the Focus post-sprint prompt, Daily Planning's Review Tasks step and Outcome peek, the Weekly Review's Someday/Maybe and Waiting For steps, and the re-clarify card. **Promotion is an explicit clarifying act**: with no current Action the user promotes a planned one directly; with a current Action, promotion is a deliberate "Replace current action" that retires the incumbent and promotes the chosen Action in one step — the system never auto-promotes. Every plan mutation (add / edit / reorder / promote / replace / demote / remove) counts as a Clarification (CONTEXT.md § Clarification), so the Outcome stops being Stale. The user can also **Abandon** the current Action outright — it leaves play with no replacement, and the Outcome is left without a current Action. Planning-ceremony integration and inter-Action dependencies are out of scope here.
* **Edits to a removed item are dropped:** When the Outcome or Capture an open screen is editing no longer exists on the device, an edit still pending on that screen (typed text, a debounced notes save, a value picked in a sheet opened before the removal) is discarded. Nothing is written or recreated, and the screen shows its "This item is no longer here" state with no recovery prompt.
* **Outcome History (Task Detail):** Directly beneath the Plan, the task-detail screen surfaces the Outcome's **history** — the chain of its terminated Actions, both completed and abandoned, newest-first with the date each ended and the time logged against it. This is the retrospection surface: it is what the user reviews to see how an Outcome actually unfolded, and the record later AI augmentation reads. It is collapsed by default, hidden entirely for an Outcome that has terminated no Action, and strictly read-only — a terminated Action cannot be edited, re-promoted, un-abandoned, or deleted, and no link is shown between an abandoned Action and its replacement (the system records none). Cross-Outcome retrospection ("what did I do this week") is future work over the same history.
* **System Views:** Auto-generated lists for 'Next' (not-done Outcomes with Intent Next that either have a current Action or wait on no Person — the one excluded case is no current Action and waiting on a Person, which surfaces only on Waiting For), 'Waiting For' (not-done Outcomes with Intent Next tagged with at least one Person, grouped by Person), and Someday/Maybe (Outcomes whose Intent is Someday/Maybe, stored as `maybe`). See CONTEXT.md § Next / Waiting For / Someday/Maybe for the List vocabulary. Next ∩ Waiting For overlaps by design when both predicates apply.
* **Record Surfaces (Done & Trash):** Two de-emphasised drawer entries (bottom of the scrollable nav column, above Settings, no count badges) open read-oriented list views: 'Done' (completed, non-trashed Outcomes, most recently completed first) and 'Trash' (Outcomes whose Intent is Trash regardless of Completion, newest-trashed first). Done and Trash are disjoint — a completed-then-trashed Outcome surfaces in Trash only. Neither view applies the context-tag filter. Rows open task detail, where a trashed Outcome can be restored to a chosen Intent (Next or Someday/Maybe) and a done Outcome restored to Next; restore clears the Outcome's Completion and counts as a Clarification. There is no purge / "empty trash" action — trashed Outcomes are kept, never deleted.
* **Sequential Logic:** Dependency tracking between Outcomes is deferred to TMaYaD/Jeeves#181 (polymorphic blockers); there is no blocked state.
* **Context Tag Cloud:** A sticky, multi-select tag filter in the primary navigation drawer. Each chip shows the context name and its active-task count; selected tags are pinned first, the rest ordered by count, capped at 12 with a Show-more toggle and a find field once more tags qualify than the cap; font size steps with relative count. Selecting one or more chips filters all list views to tasks carrying **all** selected tags (AND semantics). The filter persists across screen navigation until explicitly cleared. Long-pressing a chip opens tag management (rename, recolour, merge, delete).
* **Managing Tags, Projects and People:** Settings → Manage opens a list of every tag, project or person with its active-Outcome count; tapping an entry offers rename, merge into another entry **of the same kind**, and delete (recolour for tags only). Renaming onto a name already in use asks before merging. Merge moves every Outcome link and Capture tag hint to the target; delete removes the entry from every Outcome and Capture that carried it — an Outcome that waited only on a deleted Person stops waiting and leaves Waiting For. Nothing is ever deleted except the entry itself, merge and delete cannot be undone, and neither stamps `last_clarified_at` (a list-screen bulk edit is not thinking about each Outcome). All three sync like any other edit.
* **First-Launch Onboarding:** When there is no data and the user has never interacted with the app, an onboarding card is shown in the inbox body. The card offers three affordances: Start fresh (dismiss and use the empty inbox), Import from Nirvana export (navigate to the import screen), and Sign in to sync (navigate to the login screen). Each action permanently dismisses the card (the dismissal is kept on this device and never resets). The card also disappears automatically as soon as any item exists — a Capture in the Inbox or an already-clarified Outcome, whichever a Nirvana import produced — so the user is never shown it after their first data arrives.

### Epic 2: The Daily Execution Layer
**Goal:** Prevent overwhelm by filtering the GTD inventory into a manageable daily plan.
* **Daily Planning Entry:** Ceremonies are never auto-launched — no navigation may open one without a carried user intent; every entry is an explicit user action (button, banner, or notification action). *Carve-out:* a user-initiated, intent-carrying **sequenced entry** is allowed — when the user must close an open session before planning, completing Evening Shutdown with an and-then-plan intent routes into Daily Planning (ADR-0020); an Evening Shutdown entered this way ends without its closing animation and continues straight into planning. This is one explicit user action spread across two ceremonies, not an auto-launch; the rule continues to forbid any redirect that opens a ceremony without a carried intent. The canonical entry-point is the "Plan the Day" button on the execution home screen ("Now" — see CONTEXT.md's term-unification divergence list). Users are additionally nudged through two opt-in mechanisms:
    * **Persistent banner:** A dismissible "Plan your day →" banner shown at the top of all main views once the day's planning anchor has passed and no session has been planned since the last Evening Shutdown anchor, until dismissed for the day (there is no separate "completed" flag — an open or already-closed session started since the last shutdown anchor stands the banner down). Configurable via Settings. The banner suppresses itself when the inbox and Next are both empty while waiting-for or someday/maybe still hold items, yielding the slot to the "Start Weekly Review" banner (see Epic 5). Precedence: when the weekly review is due, the "Start Weekly Review" banner takes the slot; the Evening Shutdown banner takes precedence over the planning banner while a session is open (the two only coincide on a stale session the user must shut down first); otherwise the "Plan your day →" banner appears per its own conditions.
    * **Scheduled notification:** A local push notification at the user's configured planning time (default 08:00) with actions — Open, Snooze (configurable duration: 15 min / 1 hr / tomorrow), and Skip today. Skip dismisses the Nudge's current firing, so the banner goes too and returns at the next firing. Snooze hides the Nudge until the snooze expires and reschedules a one-off notification. All state persists across app restarts.
    * Settings: planning time, default snooze duration, default time estimate, enable/disable notification, enable/disable banner.
* **Daily Planning Ritual:** A duration-estimate intro followed by a guided 5-step wizard and a completion screen. The intro (step 0) is a briefing before the numbered steps — excluded from the progress count so the bar still reads "N of 5". It shows a Jeeves-speak sentence with a time estimate rendered inline (`2 min × (Clarify-Inbox count + Review-Tasks count) + 5 min`, the flat covering the Energy/Time check-ins and selection), rounded up to the nearest 5 and floored at 5 minutes, shown as hours and minutes (`3h 30m`) and never as a raw minute count; the counts recompute run-to-run. On a light day (no items) it shows a light-day message and the floored "about 5m", and proceeds normally — the intro never skips or dead-ends. The proceed control is Bertie speak (DESIGN.md § Voice).
    1. **Clarify Inbox (Step 1):** Process a stable snapshot of the inbox one item at a time. For each item, the user answers "What's the expected outcome?", sets fields (energy level, time estimate, due date), and routes it to one of three destinations (Next Action, Waiting For, Someday) or gives the zero-Outcome **Discard Capture** verdict — or skips it, leaving it in the inbox. Done is not a clarify-time destination: an Outcome captured already-complete is a contradiction, so completing one belongs on the Outcome's own surface. Routing to **Next** asks for the next action before it commits: the Outcome and its Action are distinct, so the user states the physical next step ("call the broker for a quote") rather than repeating the outcome ("car insurance renewal"). The prompt opens pre-filled with the title, so accepting it unchanged keeps the title as the action and the row never lands on Next actionless; cancelling leaves the item in the inbox unrouted. A due date is an attribute set alongside the routing, not a destination — there is no "Scheduled" list or state. Next step crosses into Step 2 once the cursor has walked the whole snapshot.
    2. **Review Tasks (Step 2):** The re-clarification surface. Tasks needing review — stale (worked on in a session more recently than last clarified) or actionless (no next-action phrase) — surface one at a time with a context-aware action menu ("Still relevant" / "Still waiting" / promote a queued planned Action / set or update the next action / route elsewhere). When nothing needs review, the step renders an empty-state view and the user clicks Next to advance — steps never auto-skip (CONTEXT.md § Wizard).
    3. **Energy Check-in (Step 3):** User reports today's energy level (Low / Medium / High).
    4. **Time Check-in (Step 4):** User reports today's available time (hours + minutes). Pre-filled with the available time the previous session was planned with; 8 hours when there is none.
    5. **Build Today's Plan (Step 5):** Select tasks for today from the Up Next list — individually or via long-press multi-select. In multi-select mode a contextual bar above the list shows the selected count, the previewed planned time, "Select all" / "Clear" actions, and a primary "Add to Today" button that commits the batch. The step also shows the running Today's Plan list and a capacity bar that warns if planned time exceeds available time. Selected Outcomes that carry no time estimate are counted at a configurable default (10 minutes by default, changeable in Settings); these default-counted minutes show as a lighter-blue segment of the capacity bar and are never persisted onto the Outcome. A search field under the capacity bar filters by title: Up Next matches come first, then a separate "Not in Up Next" group of Someday/Maybe and Waiting For matches (plus Next Outcomes above today's energy), and any result can be selected for today without changing its Intent.
    * **Today's Schedule (completion screen):** Rendered outside the wizard once the last step is walked — a post-ceremony confirmation, not a step. Shows the day's tasks (due-dated first, ascending, then the rest) and a calendar placeholder. "Start Day" finalises the plan, opens the FocusSession, and lands on the execution home.
* **Ceremony back navigation:** System back inside any ceremony (Daily Planning, Evening Shutdown, Weekly Review) mirrors the footer Back affordance — it retreats the per-item cursor first, then the step. When footer Back is unavailable (first step, first item — or a completion screen), system back exits the ceremony to the execution home ("Now"), never to the launcher, and abandons the performance. An abandoned performance's working state persists as an in-memory draft that seeds the next performance — re-entry resumes at the same step and item; the draft silently degrades to a fresh start after process death (accepted behaviour). Post-completion "Re-plan" still resets the ritual state before re-entering.
* **Daily Planner with Calendar Integration (TMaYaD/Jeeves#40):** Read-only external calendar (Google/Apple) rendered alongside the day's Plan. Dragging a Plan entry onto the timeline creates a **Timebox** — a scheduled start + duration on the FocusSession Plan entry, session-scoped and dying with the session (ADR-0013). When a calendar is connected, the Day Check-in derives available time from calendar whitespace instead of asking. The timeline and the calendar read ship together — without external events the Day Check-in question already delivers the capacity value. Timebox write-back to external calendars is rejected on GTD principle (ADR-0014); the sole legitimate write case — hard-landscape commitments — is TMaYaD/Jeeves#410.
* **Capacity Warning:** Visual indicators (e.g., progress bars or red text) if the total estimated time of selected tasks exceeds the available free time (calendar whitespace when connected, the Day Check-in answer otherwise).
* **Focus Mode:** A minimalist execution UI showing only the active task. Activated via a "Start" button on any task in the daily plan, or via the "Start focus" affordance on the task detail screen — which engages the task with or without an open FocusSession: with a session, the TimeLog attributes to it and the Focus pointer may reference an off-Plan task; without one, the TimeLog is ad hoc with no session attribution (ADR-0005). Displays the task title, a Jeeves-flavoured elapsed-time banner, and a sprint ring with a countdown timer. The sprint ring contains an in-ring phase-skip control: "Start break" (coffee icon) during a sprint, "Start sprint" (play icon) during a break. The bottom action bar has two controls: Stop (red outlined, returns to focus list without completing) and Done (filled blue). Done completes the current **Action** — an engagement signal, not a declaration that the Outcome is achieved, so it does not stamp re-clarification — and immediately floats the Outcome re-clarification prompt (Outcome achieved / More to do — which offers the planned queue for promotion, not only a blank field / Waiting on someone / Defer to Someday) with execution-context copy. Only "Outcome achieved" records the Outcome's Completion; dismissing the prompt leaves the Outcome Actionless and defers re-clarification to the next Daily Planning review. After a verdict (or dismissal) the session ends and advances to the next planned task. A swipe-left carousel page shows task notes (editable inline). A persistent notification appears when the app is backgrounded. The active task survives an app restart, whether it is session-backed or ad hoc ([ADR-0005](adr/0005-engagement-independent-of-focussession.md)). Sprint timer state (phase, end time, sprint/break counts, overtime start) is kept on this device, restored on restart, and not synced.
* **Session Review (Wrap-Up):** When the user taps "End Session" on the Focus screen, any unfinished tasks trigger the session review screen. For each pending task the user chooses **Done** — the same Action-complete write and verdict sheet as the Focus screen's Done, final at once — or one of three dispositions:
    * **Roll Over** — the task stays on Next and is pre-checked in the next plan summary.
    * **Leave** — return the task to Next without any change.
    * **Maybe** — defer the task to Someday/Maybe.
    Done tasks are shown in a read-only section with no chips. The "Close Session" button is disabled until all pending tasks have been assigned a disposition. If all tasks are already done, the session closes immediately without showing the review screen. Each Disposition is kept with the closed FocusSession as a historical record; a task without one has not been reviewed.

### Epic 3: Dynamic Timeboxing & Pomodoro Engine
**Goal:** Adapt rigid time constraints to varying task lengths.
* **Core Intervals:** System defaults to 20-minute focus sprints and 3-minute breaks.
* **Automated Chunking:** If a task with a 60-minute estimate is dragged to the calendar, the system automatically visually subdivides it into three 20-minute sprint blocks with break gaps.
* **Algorithmic Batching:** Suggestion engine to group multiple micro-tasks (e.g., three 5-minute tasks with the same Context) into a single 20-minute sprint block.

### Epic 4: Sprint Resolution Protocol
**Goal:** Handle incomplete work gracefully at the end of a sprint without breaking the daily calendar.
* **End-of-Sprint Interstitial:** Mandatory UI prompt when a 20-minute timer expires, blocking the break until a resolution is chosen.
* **Resolution Matrix:**
    * **Complete:** Log the sprint, complete the current Action, and float the Outcome re-clarify prompt (achieved / more to do / waiting / defer). This re-clarify prompt is **not** the End-of-Sprint Interstitial: the interstitial fires on timer expiry, is about *time* (Extend / Defer / punt), and is unimplemented; the re-clarify prompt fires on user-pressed Done regardless of the timer and is about the *Outcome*. When Epic 4 lands, its "Complete" resolution funnels into this same prompt.
    * **Extend (Bump & Continue):** Allocate another 20-minute block to the current task. The system automatically prompts the user to "punt" the lowest-priority remaining task from the day's plan to prevent calendar overrun.
    * **Defer (Log & Park):** Log 20 mins, remove from today's plan, and return it to 'Next'.
* **Estimation Analytics:** System tracks the delta between estimated and actual pomodoros to improve future AI estimations.

### Epic 5: System Integrity & The Review Guardrails
**Goal:** Prevent inventory rot through behavioral nudges and progressive friction.
* **Weekly Review Wizard:** A ceremony due seven days after completion: a duration-estimate intro, four GTD steps (Process Inbox → Review Waiting For → Review Next → Review Someday/Maybe), and a Summary. The intro is excluded from the four-step progress count. It estimates two minutes per remaining item, rounded up to five minutes with a five-minute floor, displayed as hours and minutes. Everything is the default; longer reviews offer smaller 15 / 30 / 60-minute sessions. One deterministic, swappable ranker chooses the highest-priority items across all steps; each step keeps its existing item order and review controls. Uncovered items return in later sessions, with progress surviving app restarts. An open review lasts seven days from its first partial session. Partial sessions do not stamp completion; Done on a session covering all remaining items completes the review, including when items were skipped. Ranking and coverage rules are in [CEREMONIES.md](CEREMONIES.md#weekly-review-sessions). The intro uses Jeeves speak and its proceed control Bertie speak (DESIGN.md § Voice). Capture continues through the Inbox throughout the week; there is no brain-dump step.
    * **Entry points:** A "Start Weekly Review" banner above the main views when the review is due, **or** when the inbox and Next are both empty while waiting-for or someday/maybe still hold items (in which state the daily planning banner suppresses itself, so the weekly-review banner takes its place). Plus a daily local notification at the user's configured time (default 09:00) with actions Open / Snooze / Skip today.
    * **Behaviour:** Each list-driven step iterates through items one at a time using a stable snapshot. All step snapshots are pre-loaded when the ceremony starts, so the order doesn't shift while the user is working and items routed in an earlier step (e.g. inbox → maybe) cannot leak into a later step's list. While the cursor is on a real item the footer shows Skip, which advances the cursor (Back symmetrically retreats it); once the cursor has passed the last item, Next step takes Skip's place and crosses into the following step. Inbox clarification uses the same card UI as the daily-planning ritual. Each per-item step (Waiting For, Next, Someday/Maybe) also offers a `Re-clarify…` action that opens the full clarification UI as a sub-flow over the current item; routing inside the sub-flow advances the cursor, while backing out without routing keeps the item and advances. A list-driven step whose snapshot loads empty renders an inline empty-state view; the user clicks Next to advance (steps do not auto-skip, per CONTEXT.md § Wizard). Tapping Done finalises the completion timestamp (synced across devices) and returns the user to the inbox.
    * **Persistence:** Last completion date, the Nudge's dismiss and snooze state, and notification/banner settings are stored as user preferences and replicate across devices.
* **System Trust:** The first Settings section, SYSTEM TRUST, shows two states (all good, needs attention) over the signals that exist — Captures in the Inbox (more than 50) and the Weekly Review (7 days since the last one, or since the first Capture or Outcome). One tappable row per signal opens the place to fix it; the combined state is a glyph in the header. Shape carries the state, with no number and no amber. Guardrails never block. *(Progressive Restriction levels are not planned; the Bypassed signal arrives with #107.)*
* **Stale Task Sweeper:** Forces a binary choice (Move to Maybe OR Delete) on tasks bypassed/rescheduled more than three times. *(Deferred to TMaYaD/Jeeves#107 — adds a skip count to review eligibility: clarified, unfinished Outcomes with Intent Next that are either Stale, or Actionless with no Person tag and no Clarification within the review interval (CONTEXT.md § Stale / Actionless) and prefixes Step 4 of the Weekly Review with a forced-resolution surface.)*

### Epic 6: Contextual & Geofenced Surfacing
**Goal:** Reduce cognitive load by hiding irrelevant tasks based on time and physical location.
* **Time-Bound Surfacing:** Contexts tied to hours (e.g., 'Work' tasks auto-hide at 17:00).
* **Geofenced Contexts:** Map physical locations to Contexts. App surfaces specific tasks when entering the GPS geofence.
* **Errand Handoff:** Group location-tagged tasks. Provide a single export button to pass coordinates via URL scheme to native navigation apps (Google Maps/Waze) for route optimization. *(Note: Do not build native route planning.)*

### Epic 7: Android OS Deep Integration
**Goal:** Zero-friction capture in mobile environments.
* **Native Share Sheet:** Register app as a target to parse text, URLs, and attachments directly to the Inbox.
* **Voice Assistant Intents:** `actions.intent.CREATE_THING_TO_DO` integration for hands-free capture via Google Assistant.

### Epic 8: AI-Assisted Triage (The Clarify Step)
**Goal:** Reduce the friction of organizing the Inbox.
* **Auto-Triage:** LLM parses raw inbox text and suggests Project, Context, Energy, and Duration.
* **Human-in-the-Loop:** User must explicitly approve/modify AI suggestions before committing to the inventory.
* **Conversational Capture:** Audio interface for brain-dumping, where the system prompts the user verbally to define GTD parameters.
* **Interactive Verbal Clarifier:** Structured verbal Q&A that prompts the user through GTD clarification questions for a single task, distinct from the passive conversational brain dump.
* **AI-Powered Tag Summary:** On-demand AI-generated summary of all tasks under a given tag — task count, completion status, overdue highlights, and next actions.
* **Graceful AI Degradation:** All AI-powered features must fall back gracefully when the AI service is unavailable, ensuring core GTD workflows remain fully functional without intelligence features.

### Epic 9: Habit Tracking
**Goal:** Support recurring behavioral commitments that don't fit the "complete and forget" model of a GTD task.
* **Habit Definition:** Create habits with title, frequency (daily, specific weekdays, X times per week/month), time-of-day anchor, and optional context/location link.
* **Check-In:** Binary (done/not done) or measurable (numeric value, e.g., "glasses of water: 6").
* **Streak Tracking:** Current streak, best streak, completion rate over 7/30/90 days. Flexible frequency awareness — rest days don't break non-daily streaks.
* **Visualization:** Heatmap/calendar view showing consistency over time.
* **GTD Integration:** Habits surface in the Daily Planning summary (without consuming task capacity), morning review, Evening Shutdown check-in, and context/location-based surfacing. Habits can optionally be worked on in Focus Mode with Pomodoro timing.

### Epic 10: Extended Capture Channels
**Goal:** Meet users where they are with additional low-friction capture methods beyond the core app and Android OS integration.
* **Home Screen Widget:** Quick-capture widget for task entry without opening the app.
* **Email-to-Inbox:** Forward emails to a dedicated address to create inbox items.
* **Messaging Integration:** Capture tasks via messaging platforms (e.g., Telegram bot, WhatsApp).
* **Due-date notifications:** A due-dated Outcome that is not done or trashed gets a local notification at 09:00 local time on its due day, titled with the Outcome and reading "Due today"; tapping it opens the Outcome. It is re-scheduled when the due date changes, the device timezone changes or the app restarts, and cancelled when the Outcome is completed, trashed, deleted or loses its due date. The nearest 50 are scheduled; further ones are scheduled when the app next opens or an Outcome changes, not as alarms fire. No actions or snooze yet.

### Epic 11: Data Portability & Migration
**Goal:** Reduce switching costs and prevent vendor lock-in.
* **Import from Nirvana:** One-time migration of tasks, projects, contexts, and metadata from Nirvana GTD export (CSV or JSON), preserving GTD state and hierarchy. Each source state is classified by the table below; an unclarified item becomes a **Capture** and a clarified one an **Outcome**. Clarified items are bucketed by Intent, Completion and Person tags:

| Nirvana state | Import outcome |
| :--- | :--- |
| Inbox — and any unrecognised state (e.g. CSV `active`, JSON 11 for active projects) | Becomes a **Capture** in the Inbox; its Nirvana tags (project / context / `WAITINGFOR` person) become Capture **tag hints**. Recognised states form a positive whitelist so unknowns can't slip silently into active lists. |
| Next, Waiting | Becomes an Outcome with Intent Next. A non-empty `WAITINGFOR` value becomes a person tag on the imported Outcome. |
| Someday, Inactive-Later | Clarified Outcome, Intent Someday/Maybe. |
| Scheduled, Scheduled-Repeating, Reference | Clarified Outcome, Intent Someday/Maybe, plus an `@scheduled` / `@repeating` / `@reference` context tag — Jeeves has no Scheduled/Repeating/Reference primitive, so the original category stays recoverable after import. |
| Trash | Clarified Outcome, Intent Trash. |
| Completed — Logbook, non-empty `COMPLETED` (CSV), or non-zero `completed` (JSON), regardless of state | Completion set (the completion date, or import time when unparseable), Intent Next. Completed wins: no `@scheduled`/`@repeating`/`@reference` auto-tag is injected. |

  JSON exports carry state ints rather than literals: the recognised (clarified) set is `{1–7, 9, 10}`, of which `{3, 4, 5, 9, 10}` map to Someday/Maybe and `{6}` to Trash, with auto-tags 3 → `@scheduled`, 9 → `@repeating`, 10 → `@reference`; 0 and unrecognised ints fall to the Inbox row above.

  Re-importing the same export is safe to repeat. Item ids are deterministic, so a second run lands on the rows the first run wrote and updates them in place rather than replacing them. It refreshes only what the export owns — title, notes, Completion, clarified state, due date, time estimate, energy level, capture source — while the user's own later edits survive untouched: priority, location, when the last next action was completed, and creation date. A Capture the user has since clarified likewise stays clarified and keeps its provenance links instead of being pushed back to the Inbox.

  **Imported data syncs.** Outcomes, Captures, Tags and their tag links are each recorded on the op log like any other edit ([SYNC.md](SYNC.md)), so an import performed on one enrolled device appears on every other, and a device enrolling later rebuilds it from the log alone. Importing *before* signing up for sync works too: enrolling uploads the existing store ([ADR-0034](adr/0034-sync-starts-at-enrolment.md)). Neither ordering strands data.

  **An import saves in batches, so an interrupted import keeps what it finished.** All-or-nothing over a large file could keep every item on this device while none reaches the user's other devices. Re-running the same export completes what an interruption left behind without duplicates. Project tags are saved before the first task batch, so an interruption between them can leave Tags with no Tasks — harmless, and resolved on the re-run. Nothing yet tells the user an import stopped short (TMaYaD/Jeeves#642).

  Intent survives in one direction only. A row the export buckets into Next or Waiting is left at whatever Intent the user has since given it, so a locally demoted Outcome stays demoted. A row the export buckets into Someday/Maybe or Trash is re-bucketed there on every run, so a local promotion of such a row back to Next does not survive a re-import — a known asymmetry, not a deliberate ownership rule.

* **Build version in Settings → About:** Settings → About always shows the running build's version name and build number, plus the short commit sha when the build carries one (CI builds do; local builds omit it) (e.g. `Version 1.3.0-alpha.17 (412) · a1b2c3d`), read from the build rather than a checked-in value, so a rollout can be checked from the device.

* **Export (developer options):** The app can export the current user's GTD data to a JSON file: Captures, Outcomes, Actions, Tags (Labels, Areas, Contexts, Projects, Persons), TimeLogs, FocusSessions and their links. No preference and no credential is ever exported. The export is the same encoding sync uses ([ADR-0047](adr/0047-export-is-the-op-log-wire-encoding-and-import-detects-it-silently.md)), so a round-trip loses nothing.

  **The export UI is a hidden Easter egg.** It is reached only by tapping the "Jeeves" name in Settings → About seven times (the Android developer-mode gesture), which reveals a **Developer Options** section with an *Export data* item; the unlock is session-scoped and never persisted. The file is saved through the platform save dialog, on mobile and desktop alike.

* **Import supports the Jeeves export silently:** The existing *Import from Nirvana* surface re-imports a Jeeves export with no UI or copy change and no indication that a second format — or export at all — exists. The file is recognised by its shape ([ADR-0047](adr/0047-export-is-the-op-log-wire-encoding-and-import-detects-it-silently.md)). Each imported item is saved and recorded on the op log, so it syncs to the user's other devices exactly as a Nirvana import does, and importing works fully offline on an un-enrolled device. Items are saved in batches for the same interruption safety as the Nirvana import and re-owned by the importing account. A re-import updates the same items in place rather than duplicating them — the export→import→export round-trip is byte-identical.

  **A file Jeeves cannot fully read is refused, not partly imported.** Collections renamed since the file was written are translated to their current names. A non-empty collection with no recognised name is refused by name before a single item is saved, as is one whose value is not a list of items at all. The file's format version is checked — a file from a newer format, or one that does not say in an integer which format it is in, is refused the same way. Items the file carried but the device did not keep (no usable id, or a link whose key cannot be resolved) are reported in the import summary's *Items skipped* rather than passed over. Together these prevent an import from reporting success over incomplete data.

## 5. Architectural Directives

* **Engineering:** Prioritize Local-First data storage to eliminate UI latency. Manage Intent and Completion transitions, due-date edits, and focus tracking rigidly to ensure accurate time logging.
* **Design:** Maintain a strict visual dichotomy. High information density for the GTD Inventory (planning phase) and extreme minimalism for Focus Mode (execution phase). Ensure Guardrail interruptions are clear, explaining the *why* behind the restriction.
* **Optional Authentication:** The app must be fully functional without login. Authentication is only required for cross-device sync. **Local-only is a supported steady state, not a transitional one** — a device may run local-only indefinitely, whether or not it is signed in, and the app must never treat that as a condition to be escorted out of.
* **Enrolment is opt-in:** Starting sync means enrolling the device through the **enrolment ceremony**, where it either founds the account (generating a recovery passphrase) or joins one that already exists (entering that passphrase). **No code path may route the user there.** Every entry originates in an explicit user action, from two places: the SYNC section of Settings ("Set up sync on this device", shown while the device is signed in and not enrolled) and the first-launch card ("Sign in to sync", which leads to sign-in and from there to registration). The ceremony is pushed, so backing out of it returns the user to where they were, and a signed-in device that never enters it keeps working exactly as before. Local data must be preserved: enrolling authors the whole local store onto the op log automatically, so nothing the user accrued offline is left behind (issues #591, #595, #673; ADR-0034).
* **Sync:** Real-time bidirectional sync between devices over the minimal sync server's content-blind op log (ADR-0026). The sync layer activates at **enrolment** — signing up and enrolling a device is what starts syncing, with no migration ceremony — and must handle offline write queuing (the durable outbox) and conflict resolution (field-grain last-write-wins by default, with a per-key strategy registry behind ADR-0030's lattice requirement). Sync state is presented in exactly one place, the drawer indicator, derived from the sync layer's own health; Settings offers only the next step to take — signing in, enrolling, or signing out. **The indicator is red only when something of the user's is genuinely stuck** — a refused forgery, a reorder that converged, or a key still in flight are the app working, and are reported rather than alarmed. When there is an account of events worth reading, and only then, the indicator becomes tappable and opens a **sync-health screen** that says in plain language what happened, per condition, for both of the device's Workspaces. A healthy device has no entry point, deliberately. The screen reports and offers no action: choosing how to settle a conflict is not yet built. The op log is the whole client sync stack — there is no second engine on the device (#595) — and the server keeps no domain schema: it appends and serves opaque envelopes, and the client is the source of truth for everything they carry (#556).
* **Pluggable Sync (planned):** The device database is the source of truth on every device; a sync backend only carries changes, and the app merges them with its own strategies. The op-log server is the one backend today. Candidates behind the same interface: an op-log folder synced by any file syncer, a Markdown vault (one page per Outcome, one sheet per FocusSession) readable and editable outside the app, and the roundelay service — see [proposals/sync-plugins.md](proposals/sync-plugins.md).
* **Cross-Device Settings Sync:**
    * **Storage:** User preferences (sprint/break durations, planning time, notification and banner toggles, snooze duration, default time estimate, clarify mode) and ceremony state (banner dismissed, notification skip/snooze, Evening Shutdown check-in completed — see Epic 2) are stored as synced preferences, replicated through the op log in the User-global preferences Workspace ([ADR-0027](adr/0027-workspace-as-partition-unit.md), [ADR-0033](adr/0033-user-preferences-ops-carry-their-key.md); merge rules in [SYNC.md](SYNC.md)). Sprint timer state (current phase, end time, sprint/break counts) stays on this device only and is not synced.
    * **Live updates:** A preference changed on another device takes effect here without a restart.
    * **Migration:** Upgrading from a build that kept settings only on the device carries them over into synced preferences once, on first launch. Ceremony state is also kept on the device for cold-start reads. Settings added later have no on-device predecessor; until the user first changes one, it reads as its default (1-1 clarify mode; a 10-minute default time estimate).
