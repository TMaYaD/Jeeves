# Product Requirements Document (PRD): GTD Execution Hybrid App

<!-- This document describes the current state of the system. Rewrite sections when they become inaccurate. Do not append change logs. -->

## 1. Product Vision
To build a hybrid productivity application that merges the rigid organizational trust of a Getting Things Done (GTD) inventory (e.g., Nirvana) with the focused, day-to-day execution layer of a daily planner and timeboxer (e.g., Sunsama). The system prioritizes immediate execution through Pomodoro constraints and maintains data integrity through forced behavioral guardrails.

## 2. Core Principles
* **Action over Organization:** The interface must drive the user toward execution, hiding the complexity of the larger GTD inventory during focus phases.
* **System Integrity is Paramount:** A productivity system fails when the data rots. The app will enforce necessary friction (guardrails) to ensure the user reviews and updates their inventory.
* **Local-First Performance:** Task capture and execution (timers/state changes) must work flawlessly offline to prevent user frustration.
* **Consistent Outcome representations:** Surfaces compose shared metadata, row, review-card and detail contracts; deliberate variations are recorded in [DESIGN.md](DESIGN.md#outcome-representations). Due dates use the local calendar day and `MMM d, y`.

## 3. Epics & Functional Requirements

### Epic 1: The GTD Inventory Engine
**Goal:** Establish a rock-solid backend for strict GTD methodology.
* **Universal Inbox:** A holding zone for all unprocessed captures.
* **Clarify Mode:** A synced, per-user preference (Settings → Clarify) selecting how the clarify act maps Captures onto Outcomes. **1-1 mode** (the default) clarifies each Capture to at most one Outcome: routing to an Intent creates exactly one Outcome and marks the Capture clarified (it leaves the Inbox) at that first Outcome link, while a discard is a valid zero-Outcome clarification that marks the Capture clarified without creating anything. **n-m mode** is split/merge: the user explicitly completes each Capture and only that completion marks it clarified, so a Capture stays in the Inbox while Outcomes are carved out of it. The mode changes behaviour, never stored data — toggling mid-stream leaves every existing Capture and its links to Outcomes valid.
* **Data Schema:** Tasks must support the following metadata:
    * Project
    * Area of Responsibility (AoR)
    * Contexts (Tags)
    * Time Estimate
    * Energy Level
* **Outcome Plan (Task Detail):** The task-detail screen and the Daily Planning Outcome peek surface an Outcome's **Plan** — its ordered queue of planned Actions — above the notes area. The section anchors on the current Action (with a demote affordance to move it back into the plan) and lists the planned Actions, which can be added, reordered, edited, promoted, or removed. A planned Action carries its own **energy level** and **time estimate**, set alongside its phrase in the add/edit sheet and shown on the row as chips; they travel with the Action through promotion, so estimating a step the user has not started yet is the point rather than a side effect. Planned Actions are never engageable (they do not appear on Next / Waiting For / Focus / Today's Plan), but are offered for **promotion** wherever the app asks what's next — the Outcome's detail view, the Focus post-sprint prompt, Daily Planning's Review Tasks step and Outcome peek, the Weekly Review's Someday/Maybe and Waiting For steps, and the re-clarify card. **Promotion is an explicit clarifying act**: with no current Action the user promotes a planned one directly; with a current Action, promotion is a deliberate "Replace current action" that retires the incumbent and promotes the chosen Action in one step — the system never auto-promotes. Every plan mutation (add / edit / reorder / promote / replace / demote / remove) counts as a Clarification (CONTEXT.md § Clarification), so the Outcome stops being Stale. The user can also **Abandon** the current Action outright — it leaves play with no replacement, and the Outcome is left without a current Action. Planning-ceremony integration and inter-Action dependencies are out of scope here.
* **Edits to a removed item are dropped:** When the Outcome or Capture an open screen is editing no longer exists on the device, an edit still pending on that screen (typed text, a debounced notes save, a value picked in a sheet opened before the removal) is discarded. Nothing is written or recreated, and the screen shows its "This item is no longer here" state with no recovery prompt.
* **Outcome History (Task Detail):** Directly beneath the Plan, the task-detail screen surfaces the Outcome's **history** — the chain of its terminated Actions, both completed and abandoned, newest-first with the date each ended and the time logged against it. This is the retrospection surface: it is what the user reviews to see how an Outcome actually unfolded, and the record later AI augmentation reads. It is collapsed by default, hidden entirely for an Outcome that has terminated no Action, and strictly read-only — a terminated Action cannot be edited, re-promoted, un-abandoned, or deleted, and no link is shown between an abandoned Action and its replacement (the system records none).
* **System Views:** Auto-generated lists for 'Next' (not-done Outcomes with Intent Next that either have a current Action or wait on no Person — the one excluded case is no current Action and waiting on a Person, which surfaces only on Waiting For), 'Waiting For' (not-done Outcomes with Intent Next tagged with at least one Person, grouped by Person), and Someday/Maybe (Outcomes whose Intent is Someday/Maybe, stored as `maybe`). See CONTEXT.md § Next / Waiting For / Someday/Maybe for the List vocabulary. Next ∩ Waiting For overlaps by design when both predicates apply.
* **Record Surfaces (Done & Trash):** Two de-emphasised drawer entries (bottom of the scrollable nav column, above Settings, no count badges) open read-oriented list views: 'Done' (completed, non-trashed Outcomes, most recently completed first) and 'Trash' (Outcomes whose Intent is Trash regardless of Completion, newest-trashed first). Done and Trash are disjoint — a completed-then-trashed Outcome surfaces in Trash only. Neither view applies the context-tag filter. Rows open task detail, where a trashed Outcome can be restored to a chosen Intent (Next or Someday/Maybe) and a done Outcome restored to Next; restore clears the Outcome's Completion and counts as a Clarification. There is no purge / "empty trash" action — trashed Outcomes are kept, never deleted.
* **Sequential Logic:** Dependency tracking between Outcomes is deferred to TMaYaD/Jeeves#181 (polymorphic blockers); there is no blocked state.
* **Context Tag Cloud:** A sticky, multi-select tag filter in the primary navigation drawer. Each chip shows the context name and its active-task count; every context an active Outcome carries is shown, in alphabetical order ignoring case, with font size stepping by relative count and a find field once more than 12 qualify; selected chips render as badges. Selecting one or more chips filters all list views to tasks carrying **all** selected tags (AND semantics). The filter persists across screen navigation until explicitly cleared. Long-pressing a chip opens tag management (rename, recolour, merge, delete).
* **Bulk edit from lists:** On the Next, Someday/Maybe, Waiting For and Project lists, long-pressing an Outcome enters a multi-select mode (tap toggles, deselecting the last Outcome or going back exits). A bar offers three actions on every selected Outcome: set its Project, add or remove a Tag, and set its status (Next, Waiting For, Someday/Maybe, Done, Trash). Each action is one local transaction and skips any Outcome deleted meanwhile. Project and Tag changes are Organising and never stamp `last_clarified_at`; a status change is a Clarification and stamps it exactly as the single-Outcome status change does. Done, Trash and NOW are not selectable.
* **Outcome Context-Tag Editor:** An Outcome's context tags show as the applied tags plus a dotted-circle `+`. The `+` opens the organised cloud alone, in name order, with `Find…`; a search naming no existing tag offers `Add "name"`, which creates the context tag and applies it. Tapping a tag applies or removes it; long-press recolours.
* **One Project per Outcome, across Devices:** When two Devices assign different Projects to one Outcome while apart, the most recent assignment stands on every Device after sync; only the losing link is removed.
* **Managing Labels, Projects and People:** Settings → Manage opens a list of every label, project or person with its active-Outcome count; tapping an entry offers rename, merge into another entry **of the same kind**, and delete (recolour for labels only). Renaming onto a name already in use asks before merging. Merge moves every Outcome link and Capture tag hint to the target; delete removes the entry from every Outcome and Capture that carried it — an Outcome that waited only on a deleted Person stops waiting and leaves Waiting For. Nothing is ever deleted except the entry itself, merge and delete cannot be undone, and neither stamps `last_clarified_at` (a list-screen bulk edit is not thinking about each Outcome). All three sync like any other edit.
* **First-Launch Onboarding:** When there is no data and the user has never interacted with the app, an onboarding card is shown in the inbox body. The card offers three affordances: Start fresh (dismiss and use the empty inbox), Import from Nirvana export (navigate to the import screen), and Sign in to sync (navigate to the login screen). Each action permanently dismisses the card (the dismissal syncs and never resets). The card also disappears automatically as soon as any item exists — a Capture in the Inbox or an already-clarified Outcome, whichever a Nirvana import produced.

### Epic 2: The Daily Execution Layer
**Goal:** Prevent overwhelm by filtering the GTD inventory into a manageable daily plan.
* **Daily Planning Entry:** Ceremonies are never auto-launched — no navigation may open one without a carried user intent; every entry is an explicit user action (button, banner or notification action). *Carve-out:* a user-initiated, intent-carrying **sequenced entry** is allowed — closing an open session before planning, completing Evening Shutdown with an and-then-plan intent routes into Daily Planning (ADR-0020); an Evening Shutdown entered this way ends without its closing animation, continuing straight into planning. One explicit user action spread across two ceremonies, not an auto-launch. The canonical entry-point is the "Plan the Day" button on the execution home screen ("Now" — see CONTEXT.md's divergence list). Users are additionally nudged through two opt-in mechanisms:
    * **Persistent banner:** A "Plan your day →" banner, closed with a horizontal swipe, shown at the top of all main views once the day's planning anchor has passed and no session has been planned since the last Evening Shutdown anchor, until swiped away for the day (there is no separate "completed" flag — an open or closed session started since the last shutdown anchor stands the banner down). Configurable via Settings. The banner suppresses itself when the Weekly Review banner takes its place (Epic 5). Precedence: when the weekly review is due it takes the slot; the Evening Shutdown banner takes precedence over the planning banner while a session is open (the two only coincide on a stale session to shut down first); otherwise the "Plan your day →" banner appears per its own conditions.
    * **Evening Shutdown notification:** armed wherever the Evening Shutdown banner is raised afresh and it holds the Nudge queue head: at the configured Evening Shutdown time, at an open session's due time, and at each Daily Planning time while a due session is still open. Closing the session cancels them all.
    * **Scheduled notification:** A local push notification at the user's configured planning time (default 08:00) with actions — Open, Snooze (configurable duration: 15 min / 1 hr / tomorrow), and Skip today. Skip dismisses the Nudge's current firing, so the banner goes too and returns at the next firing. Snooze hides the Nudge until the snooze expires and reschedules a one-off notification for the configured duration. The notification fires only when Daily Planning's Nudge would be visible and it holds the queue head at that time: not when there is nothing to plan, when the day's session already exists, or while another Ritual outranks it. All state persists across app restarts.
    * Settings: planning time, default snooze duration, default time estimate, enable/disable notification, enable/disable banner.
    * **Notification permission:** Every Ritual's reminder switch shows an inline row when the switch is on but the OS blocks notifications for Jeeves, with an action to ask again (or, once the OS stops prompting, a pointer to system settings). The state is re-read on app resume. Ritual reminders fire at their configured minute when the OS permits exact alarms, and may arrive late otherwise.
* **Daily Planning Ritual:** A duration-estimate intro followed by a guided 5-step wizard and a completion screen. The intro (step 0) is a briefing before the numbered steps — excluded from the progress count so the bar still reads "N of 5". It shows a Jeeves-speak sentence with a time estimate rendered inline (`2 min × (Clarify-Inbox count + Review-Tasks count) + 5 min`, the flat covering the Energy/Time checks and selection), rounded up to the nearest 5 and floored at 5 minutes, shown as hours and minutes (`3h 30m`) and never as a raw minute count; the counts recompute run-to-run. On a light day (no items) it shows a light-day message and the floored "about 5m", and proceeds normally — the intro never skips or dead-ends. The proceed control is Bertie speak (DESIGN.md § Voice).
    1. **Clarify Inbox (Step 1):** Process a stable snapshot of the inbox one item at a time. For each item, the user answers "What's the expected outcome?", sets fields (energy level, time estimate, due date), and routes it to one of three destinations (Next Action, Waiting For, Someday) or gives the zero-Outcome **Discard Capture** verdict — or skips it, leaving it in the inbox. Done is not a clarify-time destination: an Outcome captured already-complete is a contradiction, so completing one belongs on the Outcome's own surface. Routing to **Next** asks for the next action before it commits: the Outcome and its Action are distinct, so the user states the physical next step ("call the broker for a quote") rather than repeating the outcome ("car insurance renewal"). The prompt opens pre-filled with the title, so accepting it unchanged keeps the title as the action and the row never lands on Next actionless; cancelling leaves the item in the inbox unrouted. A due date is an attribute set alongside the routing, not a destination — there is no "Scheduled" list or state. Next step crosses into Step 2 once the cursor has walked the whole snapshot.
    2. **Review Tasks (Step 2):** The re-clarification surface. Tasks needing review — stale (worked on in a session more recently than last clarified) or actionless (no next-action phrase) — surface one at a time with a context-aware action menu ("Still relevant" / "Still waiting" / promote a queued planned Action / set or update the next action / route elsewhere). When nothing needs review, the step renders an empty-state view and the user clicks Next to advance — steps never auto-skip (CONTEXT.md § Wizard).
    3. **Energy Check (Step 3):** User reports today's energy level (Low / Medium / High).
    4. **Time Check (Step 4):** User reports today's available time (hours + minutes). Pre-filled with the available time the previous session was planned with; 8 hours when there is none.
    5. **Build Today's Plan (Step 5):** Select tasks for today from the Up Next list — which covers the day being planned, up to the Evening Shutdown time or, after it, the next midnight — individually or via long-press multi-select. In multi-select mode a contextual bar above the list shows the selected count, the previewed time, "Select all" / "Clear" actions, and an "Add to Today" button that commits the batch. The step also shows the running Today's Plan list and a capacity bar that warns if planned time exceeds available time (calendar whitespace, else the Day Check answer). Outcomes with no time estimate count at a configurable default (10 minutes, changeable in Settings); those minutes show as a lighter-blue segment of the capacity bar, never persisted onto the Outcome. A search field under the capacity bar filters by title: Up Next matches come first, then a "Not in Up Next" group of Someday/Maybe and Waiting For matches (plus Next Outcomes above today's energy or not open in the day being planned), any result can be selected for today without changing its Intent.
    * **Today's Schedule (completion screen):** A post-ceremony confirmation outside the wizard, not a step. Shows the day's tasks (due-dated first, then the rest) and the Plan on the day timeline (see Autoflow): the shared capacity bar, a tile at each suggested time, a "Not wholly placed" tray for an Outcome Autoflow could not place, and "Set the time" from a tile, the tray or a drag. With no calendar the day runs from now for the available time. The Now screen shows it for the open session, with a now line. Wide screens put the Plan rows beside it. "Start Day" finalises the plan, opens the FocusSession, and lands on the execution home.
* **Ceremony back navigation:** System back inside any ceremony (Daily Planning, Evening Shutdown, Weekly Review) mirrors the footer Back affordance — it retreats the per-item cursor first, then the step. When footer Back is unavailable (first step, first item — or a completion screen), system back exits the ceremony to the execution home ("Now"), never the launcher, and abandons the performance. An abandoned performance's working state persists as an in-memory draft that seeds the next performance — re-entry resumes at the same step and item; the draft degrades to a fresh start after process death (accepted behaviour). Post-completion "Re-plan" resets the ritual state before re-entering. A Daily Planning (once past its intro) or Evening Shutdown left unfinished brings its Nudge back at once in continue wording ("Push on"), even after a swipe, until the Ritual is finished; OS Notifications are unchanged.
* **Daily Planner with Calendar Integration (TMaYaD/Jeeves#40):** Read-only device calendar beside the day's Plan: Android's calendar store; iOS/Apple Calendar is out of scope until an iOS build exists; web has none. A device-local Settings switch turns it on and asks permission. Events live in memory only: never stored, synced, put in a preference, exported or logged. Only timed events block time. Re-read on open, resume and every five minutes; a re-flow that moves times shows "Very good" / "Undo", re-pinning each at its old time; a set time an event now overlaps offers "Leave it" / "Let Jeeves move it". Each Plan entry gets a **suggested time** (see Autoflow); dragging it, or "Set the time", fixes it — a start on the Plan entry, as long as the estimate, dying with the session (ADR-0013). With a calendar the day runs to the Evening Shutdown time; the Day Check shows the events and time left, not a question. Jeeves never writes to a calendar (ADR-0014), nor marks hard landscape (#410).
* **Autoflow (default suggested times):** Plan Outcomes flow onto the timeline around calendar events; a suggested time never overlaps an event unless the user sets its time explicitly. Flow fits each Outcome's estimate (no estimate uses the default) into the gaps, within its Time context or time window, re-flowing when the calendar changes. A smaller Outcome may backfill an earlier gap. Actions within an Outcome keep their order. A user-set time is pinned: it may overlap an event, never re-flowed. Only pinned starts are stored; the rest is derived per device. Past or engaged suggested times are never re-flowed. An Outcome that cannot be placed even in pieces stays in the Plan, flagged, never dropped. Guardrails nudge, never block.
* **Timeboxed, estimate as guess:** An estimate is a planning input and may be exceeded or undershot without warning. "Timeboxed" is a switch on an Action's estimate, set in the estimate tag's dialog, making it a limit; no separate duration field exists; no estimate means no limit. The limit is measured against the time logged on the Action, breaks included; a raise must exceed the time logged and starts the Sprint. Every sprint past the limit is strongly discouraged (Jeeves advice, a confirming step, escalating in tone per sprint, red overflow dots), never blocked. Carrying on regardless leaves the estimate alone; only "Raise the estimate…" changes it, for good. A sprint past the limit is not interrupted.
* **Not yet built (designed, deferred):** the batching algorithm; the Project / Outcome / Action model design sprint (Timeboxed sits on the Action meanwhile); the sprint-end resolution pass.
* **Adding to Today's Plan during the day:** While a session is open, the Now title bar's "Add" action opens "Add to Today's Plan": the user picks one Outcome (Next, or any match from the title search, including Someday/Maybe and Waiting For) and it joins the Plan, marked "Added during the day" on the Now list and both Evening Shutdown surfaces. If the unfinished Plan's estimates plus the new one exceed the time left (available time from Start Day minus time elapsed since the session started), a red note shows the totals and the button reads "Add anyway"; the add is never blocked. Engaging off-Plan still never adds to the Plan.
* **Focus Mode:** A minimalist execution UI showing only the active task. Activated via a "Start" button on any task in the daily plan, or the "Start focus" affordance on the task detail screen — which engages the task with or without an open FocusSession: with a session, the TimeLog attributes to it and the Focus pointer may reference an off-Plan task; without one, the TimeLog is ad hoc with no session attribution (ADR-0005). Displays the task title, a Jeeves-flavoured elapsed-time banner, and a sprint ring with a countdown timer. The sprint ring has an in-ring phase-skip control: "Start break" (coffee icon) during a sprint, "Start sprint" (play icon) during a break. The bottom action bar has two controls: Stop (red outlined, returns to focus list without completing) and Done (filled blue). Done completes the current **Action** — an engagement signal, not a declaration that the Outcome is achieved, so it does not stamp re-clarification — and immediately floats the re-clarification prompt (Outcome achieved / More to do — which offers the planned queue for promotion, not only a blank field / Waiting on someone / Defer to Someday) with execution-context copy. Only "Outcome achieved" records the Completion; dismissing the prompt leaves the Outcome Actionless and defers re-clarification to the next Daily Planning review. After a verdict (or dismissal) the session ends and advances to the next planned task. A swipe-left carousel page shows task notes (editable inline). A persistent notification appears when the app is backgrounded. The active task survives an app restart, session-backed or ad hoc ([ADR-0005](adr/0005-engagement-independent-of-focussession.md)). Sprints are recorded and show on every device. Sync is eventually right: a device that has not heard the latest may show a finished sprint as still running, plainly and without alarm, and the user can end it.
* **Session Review (Wrap-Up):** The Focus screen offers this entry whenever a session is open, including one with an empty Plan; Settings has none. When the user taps "End Session" on the Focus screen, any unfinished tasks trigger the session review screen. For each pending task the user chooses **Done** — the same Action-complete write and verdict sheet as the Focus screen's Done, final at once — or one of three dispositions:
    * **Roll Over** — the task stays on Next and is pre-checked in the next plan summary.
    * **Leave** — return the task to Next without any change.
    * **Maybe** — defer the task to Someday/Maybe.
    Done tasks are shown in a read-only section with no chips. The "Close Session" button is disabled until all pending tasks have been assigned a disposition. If every Outcome on the Plan, and every Outcome engaged off-Plan during the session, is already done, the session closes immediately without showing the review screen; otherwise the user goes through Evening Shutdown so each unfinished Outcome gets a Disposition. Each Disposition is kept with the closed FocusSession as a historical record; a task without one has not been reviewed.

### Epic 3: Dynamic Timeboxing & Pomodoro Engine
**Goal:** Adapt rigid time constraints to varying task lengths.
* **Core Intervals:** Defaults are a 20-minute sprint, a 3-minute short break and a 15-minute long break after every 4 sprints; all four adjustable in Settings. A sprint starts at the Settings length: stopped early it does not bring the long break closer, and run into overtime it does. The long break comes by wall time: the sprints-before-a-long-break setting is a budget of sprints × (sprint length + short break), 92 minutes at the defaults, from the last restart. The count runs across Actions and restarts only after a gap with no sprint at least as long as a long break; one cut short does not. There is no pause: the TimeLog runs through sprints and breaks.
* **Sprint count is a hint:** A row says "about N sprints" (estimate ÷ sprint length, rounded up); no estimate, no hint. Focus Mode says "Sprint N" in words, never "N of M". The dots beside the ring carry the hint visually and simply continue past it. The ring's colours, fill and direction follow the shipped clock state (blue sprint, green break, amber-to-red overtime).
* **Automated Chunking:** A gap that holds an Outcome's whole estimate is always preferred. Otherwise Autoflow splits the Outcome into pieces that fit, each its own tile. The chunking unit is one sprint plus its short break (23 minutes at the defaults), from Settings; a piece is whole units, the last with the remainder. Chunking is layout only.
* **Algorithmic Batching:** Suggest running small Actions of the same Context (10 minutes or less each) as one sprint. They stay individual tiles side by side on the timeline, with no break between them and one break after the batch. The user accepts, edits or dismisses; nothing moves unasked. The batching algorithm is not yet designed.
* **Tiles hold no sprints:** A tile is one block sized by the estimate with no sprint or break blocks inside; the sprints done in it are shown as a record, and the count ("about 3 sprints") is only a hint.

### Epic 4: Sprint Resolution Protocol
**Goal:** Handle incomplete work gracefully at the end of a sprint without breaking the daily calendar.
* **End-of-Sprint Interstitial:** Mandatory UI prompt when a 20-minute timer expires, blocking the break until a resolution is chosen.
* **Resolution Matrix:**
    * **Complete:** Log the sprint, complete the current Action, and float the Outcome re-clarify prompt (achieved / more to do / waiting / defer). This re-clarify prompt is **not** the End-of-Sprint Interstitial, which fires on timer expiry, is about *time* and is unimplemented; the re-clarify prompt fires on user-pressed Done and is about the *Outcome*. When Epic 4 lands, its "Complete" resolution funnels into this same prompt.
    * **Extend (Bump & Continue):** Allocate another 20-minute block to the current task. The system automatically prompts the user to "punt" the lowest-priority remaining task from the day's plan to prevent calendar overrun.
    * **Defer (Log & Park):** Log 20 mins, remove from today's plan, and return it to 'Next'.
* **Estimation Analytics:** System tracks the delta between estimated and actual pomodoros to improve future AI estimations.

### Epic 5: System Integrity & The Review Guardrails
**Goal:** Prevent inventory rot through behavioral nudges and progressive friction.
* **Weekly Review Wizard:** A ceremony due seven days after the last finished session (or after the first Capture or Outcome, for a new user): a duration-estimate intro, four GTD steps (Process Inbox → Review Waiting For → Review Next → Review Someday/Maybe), five when the session holds Bypassed Outcomes (Decide Bypassed Outcomes follows Process Inbox), and a Summary. The intro is excluded from the progress count. It estimates two minutes per remaining item, rounded up to five minutes with a five-minute floor, displayed as hours and minutes. Everything is the default; longer reviews offer smaller 15 / 30 / 60-minute sessions. One deterministic, swappable ranker chooses the highest-priority items across all steps; each step keeps its item order and controls. Uncovered items return in later sessions, with progress surviving restarts. An open review lasts seven days from its first partial session. Partial sessions do not stamp completion, but Done on any session counts as the last Weekly Review; Done on a session covering all remaining items completes the review, even when items were skipped. Ranking and coverage rules are in [CEREMONIES.md](CEREMONIES.md#weekly-review-sessions). The intro uses Jeeves speak, its proceed control Bertie speak (DESIGN.md § Voice). Capture continues through the Inbox all week; there is no brain-dump step.
    * **Entry points:** A Weekly Review banner above the main views when the review is due (it returns daily while due, its first line carrying the days late), when a session was started and left unfinished (it returns at once, in continue wording), **or** when the inbox and Next are both empty while waiting-for or someday/maybe still hold items Banners carry no ✕ and a Bertie-speak button; a horizontal swipe (Escape or Delete) closes the Weekly Review, Daily Planning and Evening Shutdown banners until their next firing, except an unfinished Weekly Review, which returns at once on every exit. Plus a local notification at the user's configured time (default 09:00) on each day the review is due and not dismissed or snoozed, with actions Open / Snooze / Skip this week. It yields to the Nudge queue head: while due it is the head, so the Daily Planning and Evening Shutdown notifications are withheld.
    * **Behaviour:** Each list-driven step iterates through items one at a time using a stable snapshot. All snapshots are pre-loaded when the ceremony starts, so the order doesn't shift while the user works and items routed in an earlier step (e.g. inbox → maybe) cannot leak into a later step's list. While the cursor is on a real item the footer shows Skip, which advances it (Back retreats it); once past the last item, Next step takes Skip's place and crosses into the following step. Inbox clarification uses the daily-planning ritual's card UI. Each per-item step (Waiting For, Next, Someday/Maybe) also offers a `Re-clarify…` action that opens the full clarification UI as a sub-flow over the current item; routing inside advances the cursor, backing out without routing keeps the item and advances. A step whose snapshot loads empty renders an inline empty-state view; the user clicks Next to advance (steps do not auto-skip, per CONTEXT.md § Wizard). Tapping Done finalises the completion timestamp (synced across devices) and returns to the inbox.
    * **Inbox too full:** With more than 50 Captures in the Inbox an untinted, undismissable Banner leads the Weekly Review and clears at 50 or fewer. Its Bertie button opens Inbox clarification, one Capture at a time, oldest first, until the Inbox is empty or the user leaves. The Now screen shows no Banner: the head nudge fills the Today's Tasks empty state with one full-width button (no dismiss gesture), and the title bar's sun action opens Daily Planning while Inbox too full or the Weekly Review holds that space.
    * **Persistence:** Last completion date, the Nudge's dismiss and snooze state, and notification/banner settings are stored as user preferences and replicate across devices.
* **System Trust:** The first Settings section, SYSTEM TRUST, shows two states (all good, needs attention) over the signals that exist — Captures in the Inbox (more than 50) and the Weekly Review (7 days since the last one, or since the first Capture or Outcome). One tappable row per signal opens the place to fix it; the combined state is a glyph in the header. Shape carries the state, with no number and no amber. Guardrails never block. *(Progressive Restriction levels are not planned; the Bypassed signal arrives with #107.)*
* **Bypassed Outcomes:** An Outcome that FocusSessions have passed over the configured number of times (default 3, a setting under Settings' System Trust section) since the user last engaged with it, completed an Action or decided it is **Bypassed** (CONTEXT.md § Bypassed). The Weekly Review's Decide Bypassed Outcomes step puts each to a decision: **Someday/Maybe** or **Trash** (restorable), with no skip. Each decision is logged for the System Trust Score (#52). Daily Planning never marks or holds a Bypassed Outcome.

### Epic 6: Contextual & Geofenced Surfacing
**Goal:** Reduce cognitive load by hiding irrelevant tasks based on time and physical location.
* **Time-Bound Surfacing (Time context and time window):** An Outcome's current Action can carry a **Time context** (a from-date "after Nov 30", a weekly window "Tue/Thu 09:00–17:00" in local time, not crossing midnight, or both) or a **time window**: named hours made once and attaches to many Actions, differing by day; a window past midnight belongs to its start day. While the time is unsatisfied the Outcome is hidden from the Next List; other surfaces are unchanged, except that the Weekly Review's Next step says when the time opens in the coming week, naming the window. Daily Planning's Up Next shows an Outcome whose time is open now, or opens later in the day being planned, marked "from 11:00", and once picked it is placed inside its window, leaving out one whose time does not open in it. Windows are managed under Settings → Manage, from the Time context chip on Outcome detail and the Daily Planning peek, and the **time page** shows every Outcome with a time. A one-time from-date is the optional **Follow up from** date on Waiting For. A time belongs to the Action, is not inherited by a successor, and never sits beside a window. A context tag named for a time is a Time context.
* **Places:** An Action may carry a Place, named or a pin. It leaves Next while you are elsewhere; with no location nothing is hidden by place. The place page groups nearby Places. Opt-in arrival notification, once per visit. A Habit may carry one too, never hidden by it. A named Place may carry hours (a time window's, or its own) in its own time zone, hiding its Actions on Next only; an Action's own time replaces them. All-hidden Next says so, linking Time/Places.
* **Errand Handoff:** Navigate sends chosen Places to Google Maps (past 10 stops, a route per nearby group) or Waze (next stop).

### Epic 7: Android OS Deep Integration
**Goal:** Zero-friction capture in mobile environments.
* **Native Share Sheet:** Register app as a target to parse text, URLs, and attachments directly to the Inbox.
* **Voice Assistant Intents:** `actions.intent.CREATE_THING_TO_DO` integration for hands-free capture via Google Assistant.

### Epic 8: AI-Assisted Triage (The Clarify Step)
**Goal:** Reduce the friction of organizing the Inbox.
* **Auto-Triage:** LLM parses raw inbox text and suggests Project, Context, Energy, and Duration.
* **Human-in-the-Loop:** User must explicitly approve/modify AI suggestions before committing to the inventory.
* **Conversational Capture:** Audio interface for brain-dumping, where the system prompts the user verbally to define GTD parameters.
* **Interactive Verbal Clarifier:** Structured verbal Q&A that prompts the user through GTD clarification questions for a single task, distinct from the passive conversational brain dump.
* **AI-Powered Tag Summary:** On-demand AI-generated summary of all tasks under a given tag — task count, completion status, overdue highlights, and next actions.
* **Graceful AI Degradation:** Every AI-powered feature falls back when the AI service is unavailable; the core GTD workflows stay functional without them.

### Epic 9: Habit Tracking
**Goal:** Support recurring behavioral commitments that don't fit the "complete and forget" model of a GTD task. Design and decisions: TMaYaD/Jeeves#400.
* **Habit Definition:** Title, repeat rule, anchor (including after or before another habit), Area and Labels.
* **Check-In:** Binary, or measurable against a unit and daily target.
* **Changes apply from the current period;** earlier ones keep their commitment.
* **Streak Tracking:** Current and best streak, 7/30/90-day rates. Rest days don't break streaks.
* **Visualization:** Per-habit history; any past day can be corrected.
* **From the Inbox:** Clarify a Capture into a Habit.
* **GTD Integration:** Daily Planning summary (outside task capacity), Evening Shutdown, optional Focus Mode.

### Epic 10: Extended Capture Channels
**Goal:** Meet users where they are with additional low-friction capture methods beyond the core app and Android OS integration.
* **Home Screen Widget:** Quick-capture widget for task entry without opening the app.
* **Email-to-Inbox:** Forward emails to a dedicated address to create inbox items.
* **Messaging Integration:** Capture tasks via messaging platforms (e.g., Telegram bot, WhatsApp).
* **Due-date notifications:** A due-dated Outcome that is not done or trashed gets a local notification at 09:00 local time on its due day, titled with the Outcome and reading "Due today"; tapping it opens the Outcome. It is re-scheduled when the due date changes, the device timezone changes or the app restarts, and cancelled when the Outcome is completed, trashed, deleted or loses its due date. The nearest 50 are scheduled; further ones are scheduled when the app next opens or an Outcome changes, not as alarms fire. No actions or snooze yet.
* **Follow-up notifications:** A Waiting For Outcome (open, Intent Next, waiting on a Person) whose current Action has a from-date gets a local notification at 09:00 local time on that date, titled with the Outcome and reading "Follow up today"; tapping it opens the Outcome. It is kept in step like a due-date notification and cancelled when the Action is completed or retired, the date is cleared or the Outcome stops waiting on anyone, is completed or trashed. It is independent of the due-date notification.
* **Habit notifications:** A Habit with a clock-time anchor gets a local notification at that time on each day it is for: due that day, or its weekly or monthly count unmet. A stack's notification is armed at its clock-time Habit's time and names the Habits for that day. Its button follows the first Habit: binary without an estimate, "Check in" (records the Check-in without opening the app, applied when the app next runs); binary with an estimate, "Start Focus" (opens Focus Mode on it); measurable, none. Only the coming week is scheduled.

### Epic 11: Data Portability & Migration
**Goal:** Reduce switching costs and prevent vendor lock-in.
* **Import from Nirvana:** One-time migration of tasks, projects, contexts, and metadata from Nirvana GTD export (CSV or JSON), preserving GTD state and hierarchy. Each source state is classified by the table below; an unclarified item becomes a **Capture**, a clarified one an **Outcome**. Clarified items are bucketed by Intent, Completion and Person tags:

| Nirvana state | Import outcome |
| :--- | :--- |
| Inbox — and any unrecognised state (e.g. CSV `active`, JSON 11 for active projects) | Becomes a **Capture** in the Inbox; its Nirvana tags (project / context / `WAITINGFOR` person) become Capture **tag hints**. Recognised states form a positive whitelist so unknowns can't slip silently into active lists. |
| Next, Waiting | Becomes an Outcome with Intent Next. A non-empty `WAITINGFOR` value becomes a person tag on the imported Outcome. |
| Someday, Inactive-Later | Clarified Outcome, Intent Someday/Maybe. |
| Scheduled, Scheduled-Repeating, Reference | Clarified Outcome, Intent Someday/Maybe, plus an `@scheduled` / `@repeating` / `@reference` context tag — Jeeves has no Scheduled/Repeating/Reference primitive, so the original category stays recoverable after import. |
| Trash | Clarified Outcome, Intent Trash. |
| Completed — Logbook, non-empty `COMPLETED` (CSV), or non-zero `completed` (JSON), regardless of state | Completion set (the completion date, or import time when unparseable), Intent Next. Completed wins: no `@scheduled`/`@repeating`/`@reference` auto-tag is injected. |

  JSON exports carry state ints rather than literals: the recognised set is `{1–7, 9, 10}`, of which `{3, 4, 5, 9, 10}` map to Someday/Maybe and `{6}` to Trash, with auto-tags 3 → `@scheduled`, 9 → `@repeating`, 10 → `@reference`; 0 and unrecognised ints fall to the Inbox row above.

  Re-importing the same export is safe to repeat. Item ids are deterministic, so a second run lands on the rows the first run wrote and updates them in place. It refreshes only what the export owns — title, notes, Completion, clarified state, due date, time estimate, energy level, capture source — while later user edits survive untouched: priority, location, when the last next action was completed, and creation date. A Capture the user has since clarified likewise stays clarified and keeps its provenance links instead of being pushed back to the Inbox.

  **Imported data syncs.** Outcomes, Captures, Tags and their tag links are recorded on the op log like any other edit ([SYNC.md](SYNC.md)), so an import on one device appears on every other, and a device enrolling later rebuilds it from the log alone. Importing *before* signing up for sync works too: enrolling uploads the existing store ([ADR-0034](adr/0034-sync-starts-at-enrolment.md)). Neither ordering strands data.

  **An import saves in batches, so an interrupted import keeps what it finished.** Re-running the same export completes what an interruption left behind without duplicates. Project tags are saved before the first task batch, so an interruption between them can leave Tags with no Tasks — harmless, resolved on the re-run.

  Intent survives in one direction only. A row the export buckets into Next or Waiting keeps whatever Intent the user has since given it, so a locally demoted Outcome stays demoted. A row the export buckets into Someday/Maybe or Trash is re-bucketed there on every run, so a local promotion of such a row to Next does not survive a re-import — a known asymmetry, not a deliberate ownership rule.

* **Android system backup carries no Jeeves data.** Jeeves opts out of Android's cloud backup and phone-to-phone transfer. A phone set up from another phone's backup starts as a new, empty Jeeves with its own identity. A person's data reaches a new phone through sync or the export; nothing else moves it.

* **An older build never touches data written by a newer one.** When a store carries a schema version this build does not know, neither store is opened, nothing is migrated, projected or written, and the file keeps its version and every row. The app says the data belongs to a newer Jeeves and nothing was changed.

* **Build version in Settings → About:** it always shows the running build's version name and build number, plus the short commit sha when the build carries one (CI builds do; local builds omit it) (e.g. `Version 1.3.0-alpha.17 (412) · a1b2c3d`), read from the build rather than a checked-in value.

* **Export (developer options):** The app can export the current user's GTD data to a JSON file: Captures, Outcomes, Actions, Tags (Labels, Areas, Projects, Persons), TimeLogs, FocusSessions and their links. No preference and no credential is ever exported. The export is the same encoding sync uses ([ADR-0047](adr/0047-export-is-the-op-log-wire-encoding-and-import-detects-it-silently.md)), so a round-trip loses nothing.

  **The export UI is a hidden Easter egg.** Reached only by tapping the "Jeeves" name in Settings → About seven times (the Android developer-mode gesture), it reveals a **Developer Options** section with an *Export data* item; the unlock is session-scoped and never persisted. The file is saved through the platform save dialog, on mobile and desktop alike.

* **Import supports the Jeeves export silently:** The existing *Import from Nirvana* surface re-imports a Jeeves export with no UI or copy change and no sign that a second format — or export at all — exists. The file is recognised by its shape ([ADR-0047](adr/0047-export-is-the-op-log-wire-encoding-and-import-detects-it-silently.md)). Each imported item is saved and recorded on the op log, so it syncs to the user's other devices exactly as a Nirvana import does, and works fully offline on an un-enrolled device. Imported items are re-owned by the importing account. A re-import updates the same items in place rather than duplicating them — the export→import→export round-trip is byte-identical.

  **A file Jeeves cannot fully read is refused, not partly imported.** Collections renamed since the file was written are translated to their current names. A non-empty collection with no recognised name is refused by name before a single item is saved, as is one whose value is not a list of items. The format version is checked: a file from a newer format, or one that does not name its format as an integer, is refused the same way. Items the file carried but the device did not keep (no usable id, or an unresolvable link key) are reported as *Items skipped* rather than passed over.

  **An import of a Jeeves export finishes, and says where it is.** A large file takes minutes to save, so the import reports progress as it goes and the lists fill in behind it. A record the store will not take is named in the summary, with the reason, and the rest of the file still lands: one bad record no longer stops the import.

## 5. Architectural Directives

* **Engineering:** Prioritize Local-First storage to eliminate UI latency. Manage Intent and Completion transitions, due-date edits and focus tracking rigidly, for accurate time logging.
* **Design:** Maintain a strict visual dichotomy: high information density for the GTD Inventory (planning phase), extreme minimalism for Focus Mode (execution phase). Guardrail interruptions must be clear, explaining the *why*.
* **Optional Authentication:** The app must be fully functional without login. The op log is the only thing that needs an account. **Local-only is a supported steady state, not a transitional one** — a device may run local-only indefinitely, signed in or not, and the app must never treat that as a reason to be escorted out.
* **Enrolment is opt-in:** Starting op-log sync means enrolling the device through the **enrolment ceremony**, where it either founds the account (generating a recovery passphrase) or joins one that exists (entering that passphrase). **No code path may route the user there.** Every entry originates in an explicit user action, from two places: the SYNC section of Settings ("Set up sync on this device", shown to a signed-in, un-enrolled device whose vault is off) and the first-launch card ("Sign in to sync", leading to sign-in and then registration). The ceremony is pushed: backing out returns the user where they were. Local data must be preserved: enrolling authors the whole local store onto the op log automatically, so nothing accrued offline is left behind (issues #591, #595, #673; ADR-0034).
* **Sync:** Real-time bidirectional sync between devices over the minimal sync server's content-blind op log (ADR-0026). The op-log sync layer activates at **enrolment** — signing up and enrolling a device is what starts syncing, with no migration ceremony — and must handle offline write queuing (the durable outbox) and conflict resolution (field-grain last-write-wins by default, with a per-key strategy registry behind ADR-0030's lattice requirement). Sync state is presented in exactly one place, the drawer indicator, derived from the sync layer's own health; Settings offers only the next step to take — signing in, enrolling, or signing out; the vault's tile picks a folder. **The indicator is red only when something of the user's is genuinely stuck** — a refused forgery, a reorder that converged, or a key still in flight are the app working, and reported rather than alarmed. When there is an account of events worth reading, and only then, the indicator becomes tappable and opens a **sync-health screen** that says in plain language what happened, per condition, for both of the device's Workspaces. A condition that can be settled offers that choice and clears once settled; nothing can be dismissed. The host is the whole client sync stack — one engine, with plugins as carriers (#595) — and the server keeps no domain schema (#556).
* **Pluggable Sync:** The device database is the source of truth; a sync backend only carries changes, and the app merges them with its own strategies. The op-log server is the one backend today, moving to the roundelay service (#744); an op-log folder synced by any file syncer is the other. The **Markdown vault** is the first plugin behind it: a folder of pages, one per Outcome, session and Capture, editable outside the app — not every edit is imported; [SYNC.md](SYNC.md) says which. Preferences and unnamed Tags stay on the device. One plugin runs at a time (#914). See [proposals/sync-plugins.md](proposals/sync-plugins.md).
* **Cross-Device Settings Sync:**
    * **Storage:** User preferences (sprint, break and long-break durations, sprints before a long break, planning time, Evening Shutdown time and toggles, notification and banner toggles, snooze duration, default time estimate, clarify mode, recent searches, first-launch card dismissal) and ceremony state (banner dismissed, notification skip/snooze, Evening Shutdown check-in — Epic 2) are replicated through the op log in the User-global preferences Workspace ([ADR-0027](adr/0027-workspace-as-partition-unit.md), [ADR-0033](adr/0033-user-preferences-ops-carry-their-key.md); merge rules in [SYNC.md](SYNC.md)). Only sign-in, device identity and Habits stay on one device, until Habits sync.
    * **Device names:** Each device has a name from the platform, changeable in Settings → Sync and shown on other devices.
    * **Live updates:** A preference changed on another device applies without a restart.
    * **Sign-in and sign-out:** Settings follow the device across sign-in and sign-out; every account signing in on it shares them.
    * **Migration:** Builds that kept settings on the device carry them into synced preferences on first launch. Ceremony state and the card dismissal stay on the device for cold starts. Settings added later have no on-device predecessor; until changed, they read as their defaults (1-1 clarify mode; a 10-minute estimate).
