# ADR-0048: A session Settlement is derived, and it can imply a Disposition

## Status

Accepted

## Context and decision

The Focus session needed a notion of "the user has already answered for this Outcome today" that is broader than Completion: finishing an Action and re-clarifying to *more work later*, *waiting on someone* or *defer* is an answer, and the session should stop demanding attention for it. We call that **Settled**, and we compute it rather than store it.

**Settled is derived.** An Outcome on the open session's Review surface is Settled when either its Completion is recorded, or an Action of it was completed *within this session* and it has been re-clarified at or after that completion. Every input already exists and already syncs — `actions.role` / `done_at`, `time_logs.action_id` / `focus_session_id`, `todos.done_at` / `intent` / `last_clarified_at`, the person-Tag join — so there is no column, no table, no Drift migration, no codec change, no Alembic revision and no contract-version bump. The signal survives process death and converges across Devices for free, and it cannot go stale relative to the facts it reads. The trade-off is real and deliberate: the Review summary groups by **where the Outcome stands now**, not by the verdict keystroke, so moving an item from Someday back to Next later the same day moves it between groups. That is the right reading — the summary is the day's end state — and the alternative (a recorded verdict per `(FocusSession, Outcome)`) costs a table, a codec, a migration and a contract bump to buy fidelity nobody has asked for. Reversing this later means backfilling, which is why it is written down.

**Arm two is the session-scoped negation of Stale, not "an Action was completed."** The looser reading would settle a row the user never actually answered — press Done, swipe the prompt away, and the Outcome would strike off while still owing a re-clarification. Requiring the clarify stamp *at or after* the completion mirrors `TodoDao`'s re-clarification predicate exactly, so a Settled Outcome is by construction not Stale and the two predicates can never disagree about the same Outcome on the same morning. Attribution is by **session id**, never a wall-clock window: sessions are calendar-independent and may span days (ADR-0020). Two consequences worth naming. The comparison is lexicographic over two ISO-8601 TEXT columns whose precision is not uniform — local writes keep microseconds, sync round-trips are millisecond-truncated — so two values inside the same millisecond can compare inverted; it is unreachable through the prompt (the completion and the verdict are seconds apart) and the failure direction is safe, the row reading as *not* Settled and keeping its place in the disposition step. And an **Actionless** Outcome can never settle under arm two at all: a sprint started against no current Action logs `action_id = NULL`, so no anchor exists. Marking the Outcome done still settles it under arm one.

**The bucket ladder is a presentation ordering, not List membership.** Settled Outcomes are grouped for the Review summary — Completion → done, Intent `maybe` → someday, a current Action → next, a PersonBlocker → waitingFor, otherwise next — because the summary needs one heading per item. It is not a claim about which GTD Lists the Outcome is on: Next and Waiting For overlap by design, so a mutually-exclusive bucket could not equal membership even in principle. Settling writes nothing; an Outcome's Lists are exactly what its verdict left them.

**A Settled Outcome takes an implied Disposition at Close Day.** Excluding Settled Outcomes from the disposition step means the user is never asked about them — and, left alone, they would leave Review with no **Disposition** at all, so the very item the user said "more work later" about would drop out of the Now screen's carried-over section and out of the next morning's pre-selection. So Close Day seeds them: `next → rollover`, `waitingFor | someday → leave`, `done → none`. `leave` rather than nothing, because today *every* non-completed Review-surface Outcome takes a Disposition and dropping that record would be the same class of loss with a quieter failure mode; `leave` rather than `maybe` for someday, because the verdict already set the Intent and a `maybe` Disposition would re-stamp `last_clarified_at` at close time, dragging it off the moment the user actually decided. The seed is derived fresh from the store at commit time and merged *under* the user's own choices, so an explicit tap always wins and re-entering an abandoned ritual accumulates nothing. It is written through `reviewAndCloseSession` because that is the only writer that routes a Disposition to the correct home per ADR-0016 — a Settled Outcome may be off-Plan, and the Plan never auto-grows (ADR-0002).

**Say the quiet part plainly: a future reader of the record may find a `rollover` or `leave` Disposition the user never tapped.** It was implied by an in-session Settlement, the summary told the user on screen that the re-planned group carries over, and an explicit choice always overrides it. This is why `CONTEXT.md` § Disposition no longer says a Disposition is only ever the user's Review-phase decision.

## Consequences

The Now screen's strike-off, its footer emphasis, the advance-to-next pick, the Review summary's grouping and the disposition step's contents all read one predicate, so they cannot drift. Anything that later wants to *record* a verdict rather than infer one has to backfill history that was never written. And #704 — Review stamping `last_next_action_completion_at` on Settled Outcomes, which flags them Stale the next morning — becomes a small change once this lands, because its fix consumes exactly this predicate.
