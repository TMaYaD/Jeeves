# Direct writes to a PowerSync view must self-notify Drift stream queries

In production `todos` / `tags` / `todo_tags` are PowerSync **views** with `INSTEAD OF` triggers. A Drift `UpdateStatement.write` / `DeleteStatement.go` against a view reports `changes() == 0` — the trigger body mutates the backing table, not the view — and Drift gates its built-in stream invalidation on `rows > 0`, so it never fires for these writes. That leaves the async `SqliteAsyncDriftConnection` bridge (`PowerSyncDatabase.updates` → `handleTableUpdates`) as the *only* path that refreshes view-backed watchers. When the bridge is momentarily silent — observed on the first cold start of a new planning day, during the initial-sync window (#342) — the Inbox list, Inbox badge, and Next Actions list freeze until the app restarts. The question was how to make view-backed watchers refresh reliably.

We considered leaning entirely on the bridge (the pre-#342 status quo — rejected, it is exactly what goes stale), and fixing the gate upstream in Drift so view writes notify automatically (rejected — it is a vendored-behaviour change we cannot carry cheaply, and the `changes() == 0` result is correct SQLite semantics, not a Drift bug). We chose instead to make the invariant explicit in our own code: **every `TodoDao` method that writes the `todos` view directly calls `GtdDatabase.notifyTodosViewWrite(...)` immediately after the write** (and every `CaptureDao` write calls the `notifyCapturesViewWrite()` analogue for the capture views), giving Drift a second, in-process invalidation path that does not depend on the bridge. The call is a harmless idempotent re-run under `NativeDatabase` (tests), where the underlying write already reported `rows > 0` and notified. Methods built on `customUpdate` / `customInsert` (`markDone`, `setIntent`, `restore`) notify unconditionally and are exempt.

The mechanism is covered by a deterministic regression test (`app/test/database/clarify_routing_view_notify_test.dart`) that recreates the view + `INSTEAD OF` trigger topology on a real on-disk sqlite_async database and proves the watchers go stale without the notification and refresh with it. The powersync core native lib is not loadable off-device, so a full `PowerSyncDatabase` VM test is not possible; the view+trigger model captures the exact `changes() == 0` mechanism instead. The test drives `applyRouting`, but the pattern it exercises is identical for every direct view write, so it pins the shared mechanism rather than a single call site.

The trade-off is explicit: the invariant lives in each DAO method rather than at a single choke point, so a *new* method that writes a view directly and forgets the call reintroduces the bug silently. We accept that foot-gun in exchange for a minimal, review-visible change with no vendored-behaviour risk; the helper's doc comment and `docs/ARCHITECTURE.md` both state the rule so it is discoverable. If the surface of view-writing methods grows enough that per-call discipline becomes unreliable, routing all view writes through a single notify-always wrapper (or a connection interceptor) becomes preferable and this ADR should be superseded.
