# Shared app title bar with pinned capture action

Every screen adopts one shared `AppTitleBar` widget — the Flutter analogue of a Rails nav partial — carrying a title, an optional `overline` slot (small label + optional icon above the title, e.g. the project name above a task title), and the page's actions. **Capture is a pinned icon action in a fixed, reserved slot on every screen** — rightmost when nothing overflows, and immediately left of the ⋮ (which claims the rightmost slot) when actions do overflow — never overflowed itself, at an identical position relative to the trailing edge everywhere; it is the reason the bar exists, and it supersedes the global capture FAB abandoned with PR #495 (closed unmerged). The FAB approach needed per-scaffold placement across a dozen scaffolds, bespoke content-region anchoring inside the ceremony wizard, and clearance-padding audits on every scroll view beneath it; a title-bar action rides a single shared component and collides with nothing. The capture affordance moved; the write semantics did not — the action opens the same stay-open capture sheet and write path built under #458 (a raw Capture per ADR-0006, never an Outcome).

The bar is configured **by constructor parameters passed top-down** (title, `overline`, `pageActions`, leading behaviour). The rejected alternative was a provider/`content_for`-style slot that screens write into from below. During route transitions two screens coexist, so writes-from-below produce transition flicker and slot contention (last-writer-wins races between outgoing and incoming pages); with parameters the bar a screen renders is a pure function of what that screen passed, making both bug classes impossible by construction. Pages declare their own actions (`page_actions`) in priority order after capture's pin; overflow collapses lowest-priority-first into a ⋮ menu. The action count is **budgeted by screen-width breakpoints, not measured available width** — phone gets 3 buttons total including the ⋮ more button, desktop 4–5, proportional breakpoints in between — because a fixed budget is deterministic and testable where width-measuring creates layout feedback loops and per-device surprises. Whatever width remains goes to the ellipsised title.

The ceremonies adopt the bar too — consistency over bespoke chrome — with the ceremony label as the `overline` and the step title as the title, replacing the bespoke header in `app/lib/widgets/ceremony/wizard.dart`. The step progress bar and its narration (subtitle) stay in the wizard's own content region, rendered flush beneath the bar — they are ceremony chrome. Bar surfaces follow DESIGN.md's Roundedness ruling: the canonical 2/4/6 radii scale, no pills, only genuine circles staying circular.
